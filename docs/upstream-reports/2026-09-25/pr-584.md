# PR #584: feat: pre-computed indicator interpretations (#542)

- Upstream: TauricResearch/TradingAgents#584 by @claytonbrown, opened 2026-04-20, head `90c06f0d316c`
- Size: +389 / -1 across 5 files. Not a draft. Mergeable: **CONFLICTING**. No CI checks.

## Summary

**Verdict: decline.** The PR adds a rule-based bullish/bearish/neutral label layer on top of stockstats and
puts it at the top of the Market Analyst prompt. Its Bollinger rule can never fire because of a bug. The
issue it closes (#542) was closed by a maintainer, who said indicators are already computed in code.
Berkshire already computes indicators deterministically and gives the analyst a verified snapshot.

## What it does

- `tradingagents/indicators/compute.py` loads OHLCV once with `load_ohlcv` (filtered to `curr_date`) and
  computes `rsi_14`, `macd/macds/macdh`, `boll/boll_ub/boll_lb` and `close_50_sma/close_200_sma` on one
  stockstats frame. It reads the row for `curr_date` (or the last row as a fallback) and flags a golden or
  death cross when the sign of SMA50 minus SMA200 differs between the first and last of the final 5 rows.
- `tradingagents/indicators/interpret.py` maps each value to `{signal, confidence, explanation}` with fixed
  thresholds: RSI 70/80 and 30/20, the sign of the MACD histogram, the position of price inside the Bollinger
  band, and SMA50 against SMA200.
- `market_analyst.py` prepends a "Pre-Computed Indicator Interpretations" block to the system prompt and tells
  the model "Do NOT recalculate these values". Any failure is swallowed, and the prompt is then unchanged.
- The problem it targets (issue #542) is LLMs "computing" indicators. That premise is wrong for TradingAgents,
  where `get_indicators` already returns values computed in code. The maintainer said so when closing #542
  (Yijia-Xiao, 2026-09-24).

## Soundness

- **Bug: the Bollinger signal is dead.** `compute.py:89` stores the *middle band* (`boll`) as `value`.
  `interpret.py:88` then treats it as the price, and `interpret.py:99` computes
  `(boll - boll_lb) / (boll_ub - boll_lb)`. Because the bands are symmetric, this is always 0.5. Every run
  reports "Price within Bollinger Bands (50%)" as neutral, whatever the close is. The label is
  wrong, not just missing: a close above the upper band is still reported as neutral.
- **Dead code:** `_interpret_support_resistance` (`interpret.py:130`) is never registered, and `compute.py`
  never produces `last_close`, `support` or `resistance`.
- **Look-ahead:** safe. `load_ohlcv` drops rows after `curr_date`, so the fallback `ss.iloc[[-1]]`
  (`compute.py:59`) and the crossover window `diff.iloc[-5:]` (`compute.py:102`) only see past data. The
  crossover window is the last 5 *rows*, which on a non-trading `curr_date` is still correct.
- **Confidence numbers are arbitrary.** The MACD confidence divides the histogram by `|signal|`
  (`interpret.py:70`), so it saturates when the signal line is near zero. The RSI/SMA confidences
  (0.6 to 0.9) are hand-picked constants. The prompt presents them as authoritative and forbids
  recalculation, which anchors the analyst on uncalibrated labels. That is a risk to decision quality.
- **Failure behaviour:** everything returns `{}` or is caught with a bare `except Exception: pass`
  (`market_analyst.py:42`). This is safe, but a regression would be silent.
- **Duplicate data load:** the prompt block loads OHLCV separately from the analyst's own tool calls.
  This is minor, because the loads are cached.

## Quality and maturity

- Tests: `tests/test_compute_vs_fetch.py` holds 6 integration tests that hit the network (yfinance, AAPL
  2024-01-10). None of them tests `interpret.py`, so the Bollinger bug would have gone unnoticed.
- Review: only a gemini-code-assist bot review (2026-04-20). It flagged the unreachable code and redundant I/O.
  No maintainer has reviewed it. No CI has run.
- Stale and conflicting: upstream has since refactored the Market Analyst (`TOOLS` tuple,
  `get_instrument_context_from_state`, `get_verified_market_snapshot`) and removed
  `tradingagents/dataflows/stockstats_utils.py` from `origin/main`. The issue it closes was rejected on its
  premise. It is very unlikely to merge as written.

## Value to Berkshire

Low. Berkshire already implements the separation that #542 asked for:

- `berkshire/data.py:95` `compute_indicator` computes every indicator in code (REQ-DATA-03). The tools are
  date-clamped.
- `berkshire/data.py:172` `tool_snapshot` gives the verified latest row, a fixed indicator set and the last 30
  closes as the source of truth (REQ-DATA-02). `agents/market-analyst.md` tells the analyst to ground every
  number in it and flag conflicts.

The one idea the PR adds is a set of rule-based bullish/bearish labels. These do not improve grounding, because
the numbers are already verified. They add uncalibrated confidence scores and anchor the LLM on 70/30 RSI
rules that the catalogue itself warns about ("in strong trends, RSI may remain extreme"). Berkshire is already
better here. Nothing in the PR conflicts with Berkshire's decisions (it has no execution or model change), but
it would move judgement from the agent into brittle engine heuristics, and the engine/agent split does not
favour that.

## Proposed Berkshire change

None. Berkshire's verified snapshot already covers the valid part of the PR. A small, neutral extra would be to
add a derived "close position within the Bollinger band" line or an "SMA50 vs SMA200" relation line to the
snapshot as facts, without bullish or bearish labels. Nothing shows that the analyst needs these, so they are
not proposed.

## Effort and risk

Nothing to do (S if the optional derived snapshot lines were ever wanted: `berkshire/data.py` plus an
amendment to REQ-DATA-02 and one test). Adopting the PR's label layer would carry a moderate risk of biasing
the analysts with uncalibrated signals.

## Open questions

- Would a calibration study of rule-based labels against realized alpha (for example, through
  `berkshire backtest`) show any value? Without that, the labels should not be in prompts.
- Would the upstream maintainers accept a label layer on top of `get_verified_market_snapshot`? Their comment
  on #542 suggests they would not.
