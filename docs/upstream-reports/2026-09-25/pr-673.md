## Summary

**Verdict: adapt.** Telling agents the horizon they are deciding for is a good idea, and Berkshire has a real gap here. The PR itself cannot even be imported. It has a SyntaxError in `default_config.py`, a NameError in two analysts and a TypeError in a third. It also only reaches the analysts, not the roles that make the decision. Berkshire should take the idea its own way: derive one horizon line from `holding_period_days` and inject it into every prompt.

## What it does

- Adds `investment_horizon` to `DEFAULT_CONFIG` (default `"medium_term"`), plus an `INVESTMENT_HORIZONS` dict with seven keys (`1_day` to `5_years_plus`, and `medium_term`). It adds a CLI question for it (`cli/utils.py` `ask_investment_horizon`, `cli/main.py:568-576`) and passes the answer into the config (`cli/main.py:622`, `:957`).
- `get_horizon_instruction()` (`tradingagents/agents/utils/agent_utils.py`, new, after `get_language_instruction`) reads the global config and returns a fixed text such as " Investment Horizon: 1_year. Analysis Priority: Balance: fundamental value (70%) and technical confirmation (30%)...". The PR appends it to the system prompts of the four analysts.
- The problem it solves: every run uses one implicit horizon, whatever the user intends. A day trader and a 5-year allocator get the same analysis. Issue #670 does not describe the problem at all.

## Soundness

All line numbers below refer to the head commit `b45c97e2ae0b`. The "fix" commits (`7f8ef518`, `b45c97e2`) did not fix what they say they fixed.

1. **SyntaxError on import**, `tradingagents/default_config.py:45`: `"investment_horizon": "medium_term"` has no trailing comma, so `"max_debate_rounds": 1,` on line 46 does not parse. I confirmed this with `ast.parse`. Nothing in the package imports after this change. The Gemini review flagged it, and the commit "fix: add missing imports and comma fixes" did not fix it.
2. **TypeError at runtime**, `tradingagents/agents/analysts/fundamentals_analyst.py:31-32`: `+ get_language_instruction(),` followed by `+ get_horizon_instruction()`. The comma makes `system_message` a tuple, and the unary `+` on a `str` raises `TypeError: bad operand type for unary +`.
3. **NameError**: `news_analyst.py:25` and `social_media_analyst.py:19` call `get_horizon_instruction()` but never import it (see the import blocks at `news_analyst.py:2-7` and `social_media_analyst.py:2`). Only the market and fundamentals analysts import it.
4. **CLI step order**, `cli/main.py:568-587`: "Step 9: Investment Horizon" is still printed before "Step 8". The author says they fixed this in a comment, but the head does not show the fix.
5. **Design gaps** (not crashes):
   - Only the four analysts see the horizon. The Bull and Bear researchers, the Research Manager, the Trader, the risk debaters and the Portfolio Manager never do, and they are the roles that turn evidence into a rating, sizing and a stop.
   - Settlement and reflection still score every decision over the fixed `holding_period_days`. A "5_years_plus" call is still graded on 5 trading days.
   - `1_day` "intraday / bid-ask spreads / execution timing" cannot be supported with daily yfinance bars.
   - `medium_term` duplicates `1_month` and `6_months`.
   - The 60/40 and 70/30 technical-to-fundamental weights are invented and have no basis.
   - The horizon is read from the global `get_config()`, not from graph state, so it is not in any checkpoint or run signature.
   - The README gains an unrelated "Beginner Note".
6. **Look-ahead**: the change adds no data access, so it adds no point-in-time risk.

## Value to Berkshire

- **Current state**: Berkshire has the same gap in a sharper form.
  - The Portfolio Manager emits a free-text `time_horizon` ("e.g. 3-6 months", `agents/portfolio-manager.md:32`; stored by `berkshire/decisions.py:119,126`).
  - Settlement grades that call over `holding_period_days = 5` (`berkshire/config.py:20`, `berkshire/memory.py:157`, REQ-MEM-03).
  - The daily `/loop` tick re-decides every holding each trading day (D7).
  - So the effective horizon is about one week, while no role is told this, and the Portfolio Manager is free to reason about months.
  - The Reflector prompt already hedges this mismatch (`berkshire/memory.py:180`, `agents/reflector.md:8`). That is a symptom, not a fix.
- **What telling every role the horizon improves**:
  - Decision quality: indicator choice, how much weight earnings dates and macro get, and how wide stops are.
  - Honest learning from outcomes: the call and its grade use the same window.
  - Consistency across scheduled ticks: a stable horizon means less rating churn from day to day.
- **Transferable part**: only the idea. The code, the CLI step and the weight percentages do not transfer.
- **Fit**:
  - No conflict with D1-D8. It is a context line produced by the engine and read by the agents, which keeps the engine/agent split.
  - Licence: no code would be copied, so there is no Apache-2.0 concern.

## Proposed Berkshire change

Make `holding_period_days` the single source of truth, and do not add a second, free `investment_horizon` knob that could drift from settlement:

1. `berkshire/pipeline.py`: add a `horizon_instruction(days)` helper next to `language_instruction` (`pipeline.py:103`). Example text: "Decision horizon: about N trading days. This decision will be graded on the return and alpha over the N trading days after <date>. Weigh evidence by how much it matters within that window, and state catalysts that fall inside it."
   - Append it to every prompt in `build_prompt` (the same places as `{lang}`, `pipeline.py:234-293`), so the researchers, Trader and Portfolio Manager get it too, not only the analysts.
   - Copy `holding_period_days` into `state["config"]` (`pipeline.py:172`) and add it to `signature()` (`pipeline.py:121-124`), so a resumed run cannot mix horizons.
2. `agents/portfolio-manager.md:29-32`: say that `time_horizon` should match the stated decision horizon, or explain why it differs.
3. `docs/requirements.md`:
   - Add **REQ-CTX-08**: every report-producing prompt carries the decision horizon derived from `holding_period_days`, and it is part of the run signature.
   - Amend **REQ-MEM-03** to say that the same `holding_period_days` defines the horizon the agents are told.
   - Optionally add a `--horizon-days` flag to REQ-IF-02 later. Skip it for now, because `BERKSHIRE_HOLDING_PERIOD_DAYS` already covers it (`config.py:69`).
4. Tests:
   - A `tests/test_pipeline` case asserts that the horizon line appears in the prompts for analyst, bull, trader and PM steps, and that changing `holding_period_days` changes the signature.
   - Update `docs/test-plan.md` traceability for REQ-CTX-08.

## Open questions

- Is 5 trading days the horizon the user actually wants for the eToro demo book? The daily tick suggests short-term, but D6's rating-to-target-weight mapping reads more like position investing. The horizon line will make whichever answer is chosen explicit, so choose it deliberately (for example 20 trading days).
- Should the Market Analyst's indicator choice (REQ-ROLE-06) be steered by horizon, for example no 200-SMA emphasis for a 5-day window? Leave it to the prompt line first, and add a rule only if backtests show it matters.
- If upstream later adds a real horizon-aware settlement, revisit and align.
