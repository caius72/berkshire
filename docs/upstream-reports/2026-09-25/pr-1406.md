# PR #1406: point-in-time valuation snapshot with split adjustment

Upstream: TauricResearch/TradingAgents #1406 by Jackzigen, head `e48812009514`, opened 2026-09-24.
Closes #1374, supersedes #1377 (rejected). +788 / -161 across 8 files.

## Summary

**Verdict: adapt.** Berkshire has the same gap in a worse form. Its `fundamentals` tool gives live
`marketCap`/`trailingPE`/`priceToBook` to past-dated runs and backtests, marked only as "current".
The PR's idea is right: build valuation from the close and filed figures as they stood on the date,
and report the vintage of each figure. But its P/E has the same split bug that got #1377 rejected,
so Berkshire should re-implement the idea on its own data layer and not copy this code.

## What it does

- Adds a `get_valuation` tool for the Fundamentals Analyst, routed only to SEC EDGAR
  (`tradingagents/dataflows/router.py`; default set in `default_config.py`).
- For the analysis date it computes:
  - Market cap: the last as-traded close × the newest cover-page `dei:EntityCommonStockSharesOutstanding`
    filed by then (`sec_edgar.py:504`).
  - P/B: filed stockholders' equity ÷ that share count.
  - P/E: the close ÷ the latest annual diluted EPS, falling back to a single quarter's EPS.
- Enterprise value is reported as not derivable.
- It rebuilds the as-traded close by multiplying Yahoo's retroactively split-adjusted `Close` by
  every later split (`sec_edgar.py:604`).
- It scales the share count by the splits between the cover date and the price date
  (`_split_factor`, `sec_edgar.py:610`).
- It withholds either input when it is more than 200 days old.
- Each row carries its own dates.
- The problem it solves: after #1300, past-dated runs withhold the vendor profile, which carries
  today's figures. Since then the analyst has seen statements with no price attached.
  #1374 measured the effect: 55 "valuation unavailable" statements in 12 runs, against 1 with the fix.

## Soundness

- **Market cap and P/B: correct.** Cover-date-exclusive and price-date-inclusive split windows are
  the right semantics. P/B divides dollar equity by the split-scaled count, so the two are on the
  same basis. Tests pin both sides of NVDA's 2024-06-10 10:1 split.
- **Bug: P/E is not split-reconciled** (`sec_edgar.py:319-340`, used at `:456-470`).
  - EPS comes from the newest 10-K diluted EPS filed by the date. It is never scaled by the splits
    between that period's end and the price date, but the price is the as-traded post-split close.
  - NVDA from 2024-06-10 until the FY2025 10-K (Feb 2025): the close is ~$130, the filed FY2024 EPS
    is 11.93 (pre-split), and the tool prints a P/E of ~11 instead of ~110.
  - This is the same class of error the maintainer rejected #1377 for, now in a different row.
    None of the 9 tests exercises P/E across a split.
- **Quarterly EPS fallback reads as a P/E** (`:331-340`). Price ÷ one quarter's EPS is about 4× the
  annual multiple. It is labelled "(quarterly)", but an LLM will cite it as a P/E. Issue #1374's
  reference branch builds TTM from three filed figures, which this PR drops.
- **No staleness guard on EPS or equity.** Only the price and the share count have the 200-day
  guard (`:342`, `:365`). Annual EPS can be up to ~15 months old before the next 10-K.
- **5-year window** (`period="5y"`, `:585`). The window runs back from today, so a backtest dated
  more than 5 years ago gets no close and no valuation. Readers may assume this is a vintage rule;
  it is only a limit of the window.
- **Multi-class filers.** The issue itself says Alphabet has no cover-page total. The PR drops the
  issue's fallbacks to the balance-sheet count and the diluted average. So GOOGL-type names get
  "unavailable", or a single class's count if companyfacts serves one.
- **Look-ahead safety: fine.** The split history and today's price table are used only to undo
  Yahoo's adjustment. The rules that pick the filings (by filed date) and the close (on or before
  the date) do not look past the analysis date.
- **Failure behaviour: reasonable.** Each yfinance failure degrades to "unavailable" with a
  logged warning. There are three uncached yfinance calls per invocation (history plus two
  split lookups).

## Value to Berkshire

**High on honesty about data and on backtest validity.**

- `berkshire/data.py:214-226` (`tool_fundamentals`) serves `marketCap`, `trailingPE`, `forwardPE`,
  `priceToBook`, `trailingEps` and similar fields from live `.info` for any trade date. It only
  appends `CURRENT_NOTE` (`data.py:31`).
- REQ-DATA-07 allows this ("labelled as current"). But in `/berkshire:backtest` (REQ-BT-01),
  today's multiples leak into every historical decision. That is exactly the #1300 leak upstream
  has already closed.
- So Berkshire is currently worse than upstream `main` here. Upstream withholds these fields;
  Berkshire labels them.
- Berkshire already has what a point-in-time version needs:
  - statements filtered to what was filed by the date (`filter_filed`, `data.py:229`; REQ-DATA-04);
  - the trade-date close from `history(..., auto_adjust=False)` (`data.py:70`).
- No provider or CLI plumbing needs to carry over.

## Proposed Berkshire change

Build the idea the Berkshire way, on yfinance, with no EDGAR dependency (D3):

1. **Withhold live valuation fields on past dates (S).**
   - In `tool_fundamentals` (`berkshire/data.py:220`), when `trade_date < today()`, drop
     `marketCap`, `trailingPE`, `forwardPE`, `pegRatio`, `priceToBook`, `trailingEps`, `forwardEps`,
     `dividendYield`, `fiftyTwoWeekHigh`/`Low` and similar.
   - Say in the output that they are withheld and point to the valuation tool.
   - Amend REQ-DATA-07. It currently allows labelling; for price-derived fields it should require
     withholding on past dates.
2. **New `valuation` tool (M).** Add `tool_valuation(symbol, trade_date)` in `berkshire/data.py`
   and wire it in `berkshire/cli.py` next to line 130. It computes:
   - market cap, P/B and TTM P/E from the trade-date close;
   - the latest filed diluted-EPS quarters (sum of 4, else unavailable), stockholders' equity and
     share count, from the `filter_filed` statements;
   - no single-quarter P/E;
   - explicit reconciliation of **every** per-share factor (shares *and* EPS) to one split basis using
     `Ticker.splits`;
   - the same 200-day staleness rule on all inputs;
   - each figure's date in every row;
   - EV omitted.
   Add REQ-DATA-08 for this.
3. Add the tool to `agents/fundamentals-analyst.md:12` and to the REQ-ROLE-03 data-access list.
4. Tests in `tests/test_data.py` with Yahoo-shaped tz-aware stubs:
   - a split between the EPS period and the price date (the case this PR misses);
   - a split between the share count and the price date;
   - a split on the count date;
   - stale inputs;
   - negative EPS and negative equity.
   Also add rows to `docs/test-plan.md`, and a ledger entry in `docs/upstream.md` beside UP-012.

## Effort and risk

- Effort **M**. Step 1 alone is S and removes the look-ahead leak immediately.
- The main risk is split basis. yfinance statement share counts and EPS may or may not be
  restated for later splits (see below). A wrong assumption reproduces this PR's 10× error.
- Mitigation: test the tool on a real split (NVDA around 2024-06-10, AAPL around 2020-08-31)
  before relying on it.
- Other risks are low. The tool is additive, and Step 1 only removes misleading fields from
  past-dated output.

## Open questions

- For live (today-dated) runs, should `tool_fundamentals` keep serving `.info` valuation fields,
  or use the same derived tool for consistency between live and backtest runs?
- Upstream may merge the issue author's fuller design (TTM, share-count fallbacks) instead of this
  PR. Re-check #1374 before implementing, and align the output shape if it lands.
