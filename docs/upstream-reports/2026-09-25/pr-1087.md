# PR #1087: feat(reflection): calibrate lessons with surprise ratio

Head `5f55c7db1ab6`, author gyx09212214-prog, opened 2026-06-25, last updated 2026-06-25. +150/-10 across 4 files. Fixes issue #718. Reviewed against upstream `origin/main` at `35543d0`.

## Summary

**Verdict: adapt.** The goal is right: stop lessons from rewarding lucky outcomes. The surprise ratio itself is the wrong tool, because it compares a thesis-horizon price target with a 5-day realised return. Berkshire should instead give the Reflector the move the price target implied, measured from the trade-date close, next to the settlement window. It needs no ratio and no regex.

## What it does

- At the end of a run, `extract_expected_return` (`tradingagents/graph/reflection.py:24`) works out an expected return from the rendered markdown. It first looks for an explicit "expected/projected/target return|upside|downside: X%" phrase anywhere in the PM decision or the trader plan. If none is found, it uses `(Price Target − Entry Price) / Entry Price`, with both values parsed from `**Label**: value` lines.
- The value is saved in the pending log entry as an `EXPECTED_RETURN: +x.x%` line (`tradingagents/agents/utils/memory.py:50`) and parsed back at settlement (`memory.py:286`).
- During deferred reflection, `calculate_surprise_ratio` (`reflection.py:52`) computes `|raw% − expected%| / max(|expected%|, 1)` in percentage points. The prompt then gets "Expected return at entry" and "Surprise ratio" lines, plus a system-prompt sentence: a high ratio "may reflect luck or regime noise, so do not over-credit direction alone".
- The problem it targets (issue #718) is outcome bias. A win is written up as "the setup worked" even when it won for reasons other than the thesis.

## Soundness

- **Horizon mismatch (the central flaw).** The expected return is a PM price target written for the decision's time horizon, which is often months. The realised return covers `holding_days` (default 5) trading days (`trading_graph.py:225`). Upstream main has since made that window explicit in the reflection prompt because of this very issue ("a thesis written for months is not disproved by a week"). Taken over a 5-day window, the ratio is nearly always high and points the wrong way. Example: a +12% target with a +1% week scores 0.92. The prompt then reads that as luck, when it actually means "on track, too early to tell." Only a thesis that fully played out within five days scores near 0.
- **The ratio has no direction.** A lucky win and an unlucky loss get the same score, and so does beating the target for the stated reasons. The system prompt describes only the "luck" reading, so the LLM is steered towards discounting any large move.
- **Sign lost on "downside".** `_EXPECTED_RETURN_RE` (`reflection.py:4-6`) accepts `downside` but reads the number as signed. "Expected downside: 8%" is therefore stored as **+8%**, which reverses the expectation for a Sell.
- **Loose regex takes priority.** The explicit-percentage pattern runs before the structured entry/target fields and matches the first hit anywhere in the text (`reflection.py:33`). A PM decision that quotes a debater ("the bull's target upside of 30%") overrides the actual entry and target.
- **Mismatched base.** The expected return is measured from the Trader's entry price, while the realised return starts at the trade-date close. A limit entry far from the close skews the ratio.
- **Minor issues.** The `or` chaining in `extract_expected_return` (`reflection.py:39-45`) skips a legitimate `0.0`. `_parse_entry` searches the whole entry body for `EXPECTED_RETURN:` (`memory.py:286`), so if the header block is missing, a decision text containing that token gets picked up.
- **Point-in-time safety is fine.** The expectation is recorded at decision time from the run's own outputs, so there is no look-ahead. Failure handling is fine too: when nothing parses, the prompt keeps its current shape.

## Value to Berkshire

- Countering outcome bias fits Berkshire's goal of learning from outcomes (REQ-MEM-04/05), and lessons feed the Portfolio Manager's past context.
- Berkshire already covers part of this. The Reflector is told the window may be shorter than the decision horizon (`agents/reflector.md:8-11`, `berkshire/memory.py:178-183`). The DECISION block it reads includes **Price Target** and **Time Horizon**, because the engine renders them deterministically (`berkshire/decisions.py:121-125`).
- The one missing piece is a number. The Reflector sees the target price but not the price it started from, so it cannot state how much of the expected move the window delivered. Berkshire can supply that deterministically: `settle_candidates` already holds the trade-date close (`stock.iloc[0]`, `berkshire/memory.py:146`).
- The surprise ratio and the regex parsing do not transfer. Berkshire has typed `entry_price` and `price_target` fields (`decisions.py:99`, `decisions.py:118`), so it does not need to scrape markdown.

## Proposed Berkshire change

- In `settle_candidates` (`berkshire/memory.py:151`), read the PM price target from the rendered decision. The engine writes `**Price Target**: <float|not provided>` itself, so an exact, anchored parse is safe.
- Return `start_close` and `target_move = target / start_close − 1` with each candidate.
- In `reflection_prompt` (`memory.py:178`), when a target is present, add: "Price target {t} implied {target_move:+.1%} from the trade-date close over the stated horizon ({time horizon}); the window realised {raw:+.1%}."
- In `agents/reflector.md`, add one sentence: judge the move against the target and horizon, treat a large move with no thesis evidence behind it as weak evidence either way, and do not treat a partial move as a failure when the horizon is longer than the window.
- Do not add a ratio. Do not change the log format: everything is derived at settlement from the stored decision and the prices.
- Requirements: amend REQ-MEM-04, or add REQ-MEM-08: "The reflection input shall state the price-target-implied move from the trade-date close, when a target exists." Add tests in `tests/test_memory.py` for target present, target absent ("not provided"), and a Sell with a target below the close (negative move).

## Effort and risk

- Effort **S** (under 2 h): about 15 lines in `berkshire/memory.py`, one sentence in the agent prompt, one requirement row, and three tests.
- Risk is low. The change only adds reflection input. If no target is present, the prompt is exactly as it is today.

## Open questions

- Should the Trader's `entry_price` be preferred over the trade-date close as the base? The close matches how the realised return is measured, so it is the consistent choice. The entry price is only useful as context.
- Should `time_horizon` be normalised to trading days, so the prompt can say "window covers ~N% of the horizon"? It is free text today, so skip this unless the PM schema gets a numeric horizon.
- Does the lesson categorisation in #718 (`calibration | regime | feature | risk | timing`) justify a structured Reflector output? It is not proposed here. Revisit if cross-ticker lessons prove hard to use.
