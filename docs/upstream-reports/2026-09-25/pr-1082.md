# PR #1082: feat(trader): add probability + risk/reward review to every proposal

Upstream: TauricResearch/TradingAgents#1082 by @ydhawesome, head `1f2374963d51`, opened 2026-06-24, last activity 2026-06-25. Three files, +171/-5.

## Summary

**Verdict: adapt.** The useful part is a small one: the engine, not the model, works out the risk/reward from the Trader's entry, stop and target levels. Berkshire should do this with direction-aware checks, and should leave out the win probability and the bull/bear fields. The model's win probability is uncalibrated, and the bull/bear fields repeat the debate that already runs before the Trader.

## What it does

- It adds three required fields to `TraderProposal` (`bull_case`, `bear_case`, `win_probability` 0-100) and one optional field, `target_price`. `target_price` goes through the existing nullish-float coercion (`tradingagents/agents/schemas.py:139-183` at the PR head).
- A new `_render_trade_review()` (`schemas.py:189`) adds a "Probability & Risk/Reward" section to the rendered proposal. The section shows the model's win probability. When entry, stop and target are all present, it also shows three values computed in code: R/R = reward/risk, EV in R-multiples = p·RR − (1−p), and breakeven win-rate = 1/(1+RR). Each value is labelled favorable/unfavorable or above/below breakeven. When a level is missing, the section shows `n/a`.
- It adds one sentence to the Trader system prompt in `tradingagents/agents/trader/trader.py`: argue both sides, commit to a probability, and give entry/stop/target for Buy/Sell.
- The problem it addresses: Trader proposals argue only one side, and any risk/reward numbers in them are hallucinated. Computing the arithmetic in code keeps it consistent.

## Soundness

- **Bug: direction is ignored.** `schemas.py:207-208` uses `abs(target - entry)` and `abs(entry - stop)`. Inverted levels therefore produce a positive R/R and can be labelled "favorable": for example a Buy with its stop above entry or its target below entry, or a Sell with the mirror image. A reviewer (gyx09212214-prog) and the Gemini bot both reported this. It is still unfixed. The code should check the order of the levels for each action and show `n/a` plus a warning when they are inverted.
- **Probabilities given as fractions.** A model that returns `0.65` passes the `ge=0, le=100` bound (`schemas.py:153`) and is shown as "1%". The bot review points this out too. It is unfixed.
- **Uncalibrated probability shown as analysis.** The EV and breakeven values are only as good as `win_probability`, and nothing measures that number against outcomes. The prompt line "Do not default to 50 — commit" pushes the model toward confident numbers. Because EV is computed in code, a guess ends up looking like a computed result. The EV formula also assumes a binary outcome: the trade hits either the target or the stop. It ignores time exits and slippage. That assumption is acceptable, but the output should say so.
- **Hold is forced into the same shape.** A Hold must still give a win probability, although a Hold has no directional thesis for the probability to refer to.
- **Breaking schema change.** Making the three new fields required means any structured output that lacks them fails validation. Upstream then falls back to free text through `invoke_structured_or_freetext`, so an older or weaker provider loses the structured proposal completely instead of losing only the new fields.
- **Look-ahead.** None. The change only does arithmetic on levels the model already gave.

## Quality and maturity

- Tests: five updated and three new unit tests in `tests/test_structured_agents.py`. They cover the R/R, EV and breakeven arithmetic, the favorable/unfavorable labels, the `n/a` path, and `target_price` coercion. There are no tests for inverted levels or for fractional probabilities.
- CI: no status checks ran.
- Review: two comments (one bot, one community) that ask for the direction fix. No maintainer has responded. The author has not replied in three months.

- Chance of merging as-is: low. If it does merge, it will probably change first: direction checks, and possibly an opt-in flag, which the author offered.

## Value to Berkshire

- **Grounding: real value.** Berkshire's Trader already gives absolute entry and stop levels (`agents/trader.md:12`), and the Portfolio Manager gives a `price_target` (`berkshire/decisions.py:118`). Nothing computes the risk/reward those levels imply. The risk debaters and the PM currently read levels with no arithmetic next to them. A direction-checked R/R line computed by the engine in `3_trading/trader.md` would give them a number they can rely on. It fits the engine/agent split, which says deterministic numbers belong in `berkshire/` and not in model prose.
- **Risk control: small value.** The risk gate already checks that the Trader's stop is below the ask (`berkshire/orders.py:66-76`). It takes the PM target as take-profit only when that target is above the ask (`orders.py:81-82`). An R/R figure in the gate's `reasons` would make a queued order easier to judge at `/berkshire:approve`. A minimum-R/R veto is possible later, but a threshold would be a new policy decision (D5), so it is not proposed now.
- **Bull/bear fields: little value.** In Berkshire the Trader's prompt already contains the full bull/bear debate and the Research Manager's plan (REQ-FLOW-01). Asking the Trader to restate both cases adds tokens, not evidence.
- **Win probability: negative value for now.** An uncalibrated probability that feeds an EV labelled "favorable" works against honesty about data. It would be worth something only if settlement scored it, for example with a Brier score next to alpha in the decision log (REQ-MEM-03/04). That is a separate and larger idea.
- **Fit.** There is no conflict with Claude-only models, demo-first execution or human approval. The gate is long-only (REQ-RISK-04), so only the Buy ordering check matters for orders. The rendered R/R should still handle Sell, because the Trader can propose one. Licence: Berkshire re-implements roughly ten lines of arithmetic and copies no code.

## Proposed Berkshire change

1. `agents/trader.md`: add an optional `"target_price"` to the JSON block, as an absolute level in the same wording as entry/stop.
2. `berkshire/decisions.py:96-111`: `validate_trader_proposal` accepts `target_price` through `optional_float` (REQ-OUT-03). `render_trader_proposal` adds a **Risk/Reward** line computed in code. It is shown only when entry, stop and target are all present and correctly ordered for the action (Buy: stop < entry < target; Sell: target < entry < stop). Otherwise the line reads "n/a (levels missing or inverted)". No probability and no EV.
3. `berkshire/orders.py:81-84`: add `reward/risk` from ask, stop and take-profit to `reasons` when both are set (REQ-RISK-09). No new veto.
4. Requirements: amend REQ-OUT-01 (the TraderProposal schema gains `target_price`, and its rendering includes the engine-computed R/R) and REQ-OUT-03 (price fields include `target_price`). Add a test for REQ-RISK-09 that covers the R/R reason. Tests cover a valid Buy, a valid Sell, an inverted Buy, an inverted Sell, a missing target, and stop == entry.

Out of scope: `bull_case`, `bear_case` and `win_probability`. Reconsider `win_probability` only together with Brier scoring at settlement.

## Effort and risk

Effort **S** (under 2 h): one persona edit, about 20 lines in `decisions.py`, 3 lines in `orders.py`, and 6 unit tests plus the traceability rows. Risk is low. The new field is optional, so existing runs and the free-text fallback (REQ-OUT-02) are unaffected. The only behaviour change in the gate is an extra reason string.

## Open questions

- Is a minimum-R/R veto in the risk gate wanted, and if so, what should the default be (for example 1.5)? This needs a D5-style decision.
- Is it worth scoring a Trader or PM win probability at settlement (Brier score), which would make calibrated probabilities useful later?
