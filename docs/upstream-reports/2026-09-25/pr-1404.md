# PR #1404: Add optional Jev debate gate (early stop when the bull/bear case is decision-ready)

Head `78eb1adbc81c` · author kiminbean · opened 2026-09-24 · +193/-2 · 5 files

## Summary

**Verdict: decline.** An external classifier cutting the bull/bear debate short saves tokens, not
decision quality, and building it into Berkshire would break deterministic routing (REQ-FLOW-08) and
add a second model vendor for a cost problem Berkshire does not have.

## What it does

After each complete investment-debate round (`count` even, at least 2, below the round cap),
`ConditionalLogic.should_continue_debate` calls an injected gate
(`tradingagents/graph/conditional_logic.py:27-33`). The gate sends TypeSafe's Jev one `noul`
question about the tail of the bull and bear histories: "is the case decision-ready for the
Research Manager?" (`tradingagents/agents/debate_gate.py:27-41`). It reuses `post_screen.system_one`
for the HTTP call and retries. A yes with `noul >= 0.65` routes straight to the Research Manager.
It is off by default (`jev_debate_gate: False`, env `TRADINGAGENTS_JEV_DEBATE_GATE`) and does nothing
without `TYPESAFE_API_KEY` (`trading_graph.py:93-97`). The problem it solves is cost and latency:
with slow reasoning models, one debate round is two expensive LLM calls. It fixes no quality failure.

## Soundness

- **Uncaught TypeError on a null or non-numeric answer.** `return ready >= _CONVERGED_ABOVE`
  (`debate_gate.py:68`) sits outside the `try` at `:60-67`. `post_screen._answers` only checks each
  answer's `type`, not that `noul` is a number, so a `{"type": "noul", "noul": null}` answer raises
  inside a LangGraph conditional edge and fails the run. That breaks the PR's own "degrades to fixed
  rounds" promise. The fix is to move the comparison inside the `try`.
- **Docstring does not match the code.** The docstring says the gate "never returns False"
  (`debate_gate.py:48`), but `:68` returns False below the threshold. This does no harm, because the
  router tests `is True` (`conditional_logic.py:32`).
- **Truncation keeps the tail.** Each side keeps its last 4,000 characters (`debate_gate.py:55-56`).
  From round 3 on, the opening case, which usually holds the core claim, may be cut. The judge is then
  asked whether "each side's core claim ... is on the table" without seeing it, which pushes it
  toward "not ready" or makes its answer arbitrary.
- **Does nothing at the default setting.** `max_debate_rounds` defaults to 1, so the cap check
  (`conditional_logic.py:23-26`) returns before the gate is ever consulted. It only matters at 2
  rounds or more.
- **Blocking latency.** A failing TypeSafe call retries up to 3 times with a 15 s timeout, and backoff
  or `Retry-After` can add up to 30 s. That is roughly a minute and a half of blocked routing per
  round, which is the opposite of the latency saving the PR claims.
- **Not deterministic.** The same state can route differently between runs, and nothing in the state
  records that the debate ended early. The Research Manager is not told, and the checkpoint and
  replay show only a shorter history. There is no look-ahead risk, because the gate sees only the
  transcript.
- The mid-round guard and the rule that the cap beats the gate are correct and tested.

## Quality and maturity

Nine network-free unit tests (`tests/test_debate_gate.py`) cover routing, the key-less factory, error
degradation and the env override. None covers the null-`noul` path above. No CI checks have run, and
there are no reviews or comments. The PR was opened a day ago by an outside contributor. It builds on
the maintainers' own Jev integration (post screening, v0.5.1), which makes a merge plausible, but
the thresholds (0.65, 4,000 characters) are unmeasured constants and likely to change in review.
Neither the PR nor its tests show evidence that stopping early preserves the final decision.

## Value to Berkshire

Low.
- Berkshire's debate turns are Claude subagent calls under the user's Claude Code plan, and the
  default depth is 1 round. Saving one Bull+Bear pair at Medium or Deep depth is not a problem worth
  a vendor.
- It adds risk to decision quality. At Medium or Deep depth the user chose more rounds on purpose,
  and a cheap classifier overriding that choice ("REQ-FLOW-07: Shallow/Medium/Deep map to 1/3/5") is
  the wrong way round.
- It conflicts with Berkshire's decisions. Routing must be "deterministic and computed from
  persisted state only" (REQ-FLOW-08, `berkshire/pipeline.py:204-224`). The debate length is fixed at
  `2 × max_debate_rounds` (REQ-FLOW-03), and the status view assumes that too
  (`berkshire/pipeline.py:449-451`). Berkshire is Claude-only, and it already tracks TypeSafe/Jev as
  an undecided extra vendor (`docs/upstream.md` UP-017, `candidate`).
- A Berkshire-native version is possible: a Haiku "convergence" step whose verdict is persisted as a
  step output and read by `next_steps`. It would still trade debate depth for tokens with no evidence
  that the decision survives. Berkshire is not worse off without it.

## Proposed Berkshire change

None. The ledger should record PR #1404 as `declined` next to UP-017. The reasons are an extra
vendor, non-deterministic routing against REQ-FLOW-08, a token saving Berkshire does not need, and
no evidence that the final decision is unchanged.

## Effort and risk

Not adopting costs nothing. A Claude-native adaptation would be M (a new `debate-judge` step, a new
routing branch in `next_steps`, amendments to REQ-FLOW-03 and REQ-FLOW-07 and a new REQ, tests, and
status-view changes). Its risk is medium: debates silently get shorter, and the rating may drift in
backtests.

## Open questions

- Is there any measurement, upstream or anywhere else, of how often an early-stopped debate leads the
  Research Manager to a different rating than the full-length debate? That result would reopen this.
- Will upstream fix the uncaught comparison at `debate_gate.py:68` and keep the opening arguments,
  not only the tail, before merging?
