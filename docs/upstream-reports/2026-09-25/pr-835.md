# PR #835: feat(fundamentals): add earnings-context tool for catalyst awareness (#561)

Head `148b2b62f517`, author 2001adarsh, opened 2026-05-14, last updated 2026-05-14. +462/−5, 7 files. Closes issue #561.

## Summary

**Verdict: adapt.** Earnings proximity is a real blind spot in both TradingAgents and Berkshire. The PR's implementation is not point-in-time safe: it leaks actual EPS in backtests and gives a wrong next-earnings date for any past analysis date. Berkshire should build the idea on `Ticker.get_earnings_dates()`, which is keyed on announcement dates, and not port this code.

## What it does

The PR adds a `get_earnings_context(ticker, curr_date, near_earnings_window=5)` yfinance tool for the Fundamentals Analyst. It returns one markdown string with four sections:

1. The next earnings date from `Ticker.calendar`, the number of business days until it (`pandas.bdate_range`), and a YES/NO "near earnings" flag.
2. Consensus EPS and revenue estimates (`earnings_estimate`, `revenue_estimate`).
3. The last 4 quarters of EPS surprise (`earnings_history`), filtered to `index <= curr_date`.
4. The sell-side rating distribution (`recommendations_summary`, falling back to `recommendations`).

Each section fails on its own and prints `(unavailable)`. The tool never raises. The problem it addresses (issue #561): a BUY issued two days before a ±10–20 % earnings move, with no awareness of that binary catalyst.

## Soundness

- **Look-ahead leak in the surprise history** (`tradingagents/dataflows/y_finance.py:541-547` at head). `earnings_history` is indexed by **fiscal quarter end**, not by report date. The filter `hist.index <= curr_ts` keeps a quarter that ended on 03-31 even when `curr_date` is 04-10 and the company only reports on 04-25. The row's `epsActual` and `surprisePercent` are then future information. The PR body calls this "look-ahead-safe", which is wrong for about 3–6 weeks after every quarter end. Berkshire's `filter_filed` avoids the same trap for statements with a filing lag (`berkshire/data.py:229-233`, REQ-DATA-04).
- **Wrong next earnings date for past dates** (`y_finance.py:498-509`). `Ticker.calendar` holds only the event that is upcoming *today*. For a backtest date, the tool reports today's next event (months later, "NO" flag) and misses the report that actually followed `curr_date`. That is not a leak, but the flag is silently wrong in exactly the mode where the catalyst logic would be evaluated. Also, `earnings_history` only covers the last ~4 quarters counted from today, so for dates more than a year back the section is empty.
- **Current snapshots are not labelled in the output.** The docstring (`y_finance.py:477-483`) admits that consensus and recommendations are current snapshots, but the returned markdown never says so (`y_finance.py:520`, `:568`). The LLM sees today's consensus and today's rating counts as if they were as-of `curr_date`. `recommendations_summary` periods (`0m`, `-1m`) are relative to today too. Berkshire requires such data to be labelled (REQ-DATA-07).
- **Trading-day count** uses `bdate_range`, which ignores holidays. It is off by one across a holiday, which is acceptable for a ±5 flag.
- **Timezones**: the second commit (`148b2b62f517`) strips tz before comparing, which resolves the Gemini bot's TypeError concern.
- **Failure behaviour** is good: every surface is wrapped, and the tool returns a string.
- The flag only reaches the Fundamentals report. Nothing tells the Trader, the risk debaters or the PM to act on it. Whether it changes sizing depends on the Fundamentals Analyst mentioning it and later roles picking it up.

- No CI checks ran. The only review is the Gemini bot. There is no maintainer response in 4+ months.
- `mergeable: CONFLICTING`. Upstream also added `tests/test_fundamentals_lookahead.py`, so the maintainers care about exactly the leak this PR has.
- Merge likelihood as is: low. It needs a full rewrite onto the new vendor layout, and a point-in-time review would probably fail it.

## Value to Berkshire

High for decision quality and risk control. Berkshire has no earnings awareness at all:

- `grep` finds no earnings date or catalyst handling in `berkshire/` or `agents/`.
- `tool_fundamentals` shows only `trailingEps`, `forwardEps` and `earningsGrowth` from `info` (`berkshire/data.py:214-226`).
- The risk gate (REQ-RISK-01..09) sizes opens without regard to an imminent report.

A scheduled daily tick is exactly where "Buy two days before earnings" happens. Knowing the surprise track record (from announcements before the trade date) is also useful grounding. The consensus and rating snapshot is of lower value: it is only valid for live runs and duplicates what the News and Sentiment analysts can find on the web.

Berkshire is already stricter on point-in-time data (REQ-DATA-01/04/07) than this PR, so porting the code would weaken Berkshire.

## Proposed Berkshire change

Adapt the idea the Berkshire way:

1. **`berkshire data --run RUN earnings SYMBOL`** (`berkshire/data.py` new `tool_earnings`, `berkshire/cli.py` dispatch next to `insider` at `:134`):
   - Use `Ticker.get_earnings_dates(limit=…)`, which is indexed by **announcement date** and covers past and future events.
   - Next event = the first announcement date later than `trade_date`, with trading days until it and a near-earnings flag (`earnings_window_days`, default 5). Label the date as an estimate, and label it current when `trade_date < today`, because today's schedule may differ from what was known then.
   - Surprise history = the last 4 announcements with a date on or before `trade_date` (reported EPS, estimate, surprise %). This is point-in-time correct by construction.
   - Consensus estimates and the rating distribution: include them only when `trade_date == today`. Otherwise print one line saying they are unavailable as-of that date (REQ-DATA-07 style), rather than printing current data.
   - Crypto and instruments without data: a readable "no earnings calendar" line (REQ-DATA-06).
2. **Fundamentals Analyst** (`agents/fundamentals-analyst.md:12,26`): add the tool and ask the analyst to state the earnings proximity explicitly in the report and its end table.
3. **New requirement REQ-DATA-08**: "Earnings context shall key events on announcement dates. Surprises announced after the trade date shall be omitted. Consensus and rating snapshots shall be shown only for a same-day run, and shall otherwise be marked unavailable." Amend REQ-ROLE-03 (Fundamentals data access). Add tests with a mocked `get_earnings_dates` covering: a quarter ended before the trade date but reported after it is excluded, the next-event day count, and a past date that gets no consensus.
4. **Optional follow-up, behind a user decision:** a risk-gate rule (REQ-RISK-10) that halves `target_weight` for opens within the earnings window, or vetoes them. This is the deterministic part of what the issue actually wants. Berkshire's engine/agent split makes it cheap and testable, but it changes D6 semantics, so ask first.

## Effort and risk

- Steps 1–3: **M** (about a day, including tests and the traceability rows). Low risk: a new read-only tool, and the existing tools are untouched.
- `get_earnings_dates` scrapes Yahoo's earnings calendar. It is flakier than the `info` fields and sometimes rate-limited, so the fail-open path matters.
- Step 4 is S once decided, but it has policy risk: it could suppress good entries, and it needs backtest evidence (REQ-BT-03 per-rating alpha, split by near/far earnings).

## Open questions

- Should near-earnings awareness stay advisory (analyst report → PM), or become a deterministic gate rule? That is a user decision, because it touches D6.
- How reliable is the `get_earnings_dates` history depth for non-US tickers (`.DE`, `.L`), which the eToro watchlist uses? Check on a few symbols before committing to REQ-DATA-08 wording.
- Should the PM receive the near-earnings flag directly as structured context (like REQ-CTX-04 portfolio context), so it does not depend on the analyst mentioning it?
- Upstream may yet land its own version on the new vendor layout (`vendors/yahoo/fundamentals.py`). If it does and is point-in-time safe, re-check it against this design.
