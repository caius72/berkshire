# TradingAgents PR #302: ACE - Agentic Context Engineer

- Head: `c510a8721ada` (author EduardGilM, opened 2025-12-25, last activity 2026-01-18)
- Size: +462 / -12 across 8 files, no tests. Not a draft, mergeable state `CONFLICTING`, no CI runs.
- PR files cited below are at the head commit. Berkshire files are at `main`.

## Summary

**Verdict: decline.** The PR adds a global, ungrounded "skillbook" that an LLM writes by grading its
own analysis for consistency, with no outcome signal. The Reflector never sees the reports it is
meant to check. The skillbook has no point-in-time filter, and the code does not import against the
current `ace-framework`. Berkshire's outcome-settled, `as_of`-filtered lesson loop (REQ-MEM-03..08)
already does the useful part of this, and does it better.

## What it does

- After each CLI analysis, `TradingAgentsGraph._ace_learn_from_analysis`
  (`tradingagents/graph/trading_graph.py:292`) packs the four analyst reports, the investment plan and
  the final decision into a Kayba `ace-framework` `Sample`. `TradingACE.learn_from_analysis`
  (`tradingagents/ace/kayba_ace.py:98-166`) then runs ACE's Reflector with a fixed rubric ("is the
  decision logically consistent with the reports, regardless of the price outcome",
  `kayba_ace.py:42-52`). ACE's SkillManager turns the critique into "strategies", which it appends to
  a single JSON skillbook (`results/ace_skillbook.json`).
- When the graph is built, `skillbook.as_prompt()` is appended to the **Trader's** user prompt as
  "Learned Trading Strategies (ACE)" (`tradingagents/graph/trading_graph.py:140`,
  `tradingagents/graph/setup.py:100`, `tradingagents/agents/trader/trader.py:26-32`).
- A second hook in `reflect_and_remember` (`_ace_learn`, `trading_graph.py:320`) is meant to learn from
  realised returns too. In practice it drops them (see Soundness).
- The claimed problem: price-outcome learning is noisy, so learn "analytical consistency" instead.
  No issue is linked, and no evidence was offered that it helps. A 2026-01-18 request for backtest
  results got no reply.

## Soundness

Concrete defects:

1. **The Reflector is blind to the evidence.** The reports go into `Sample.context`
   (`kayba_ace.py:106-120`). `reflector.reflect(...)` gets only `question`, an `AgentOutput` whose
   reasoning is the placeholder string `"Full analysis process for {ticker}."` (`kayba_ace.py:124-126`),
   the decision, and the fixed rubric (`kayba_ace.py:137-143`). In `ace-framework` 0.12 the Reflector
   prompt uses only `agent_output.reasoning`, `final_answer`, the ground truth, the feedback and the
   skillbook, and it drops extra kwargs (`ace/implementations/reflector.py:77-120`). So the "is the
   decision consistent with the reports" check runs without the reports. Only the SkillManager sees
   them, as `question_context`.
2. **No ground truth at all.** `TradingEnvironment.evaluate` (`kayba_ace.py:37-52`) returns the same
   feedback and the same "a logically sound thesis" ground truth for every run. The learning signal is
   an LLM's opinion of an LLM's output, with nothing to anchor it. Rules can pile up that sound good
   but pull the wrong way.
3. **The outcome path discards the outcome.** `_ace_learn` passes `result=str(returns_losses)`
   (`trading_graph.py:320-341`). `TradingACE.learn_from_trade` accepts `result` and never uses it, and
   it files all four concatenated reports under `"market"` (`kayba_ace.py:169-178`). The only
   price-grounded path is dead.
4. **Look-ahead leakage.** There is one skillbook per `results_dir`, with no dates on the skills and no
   `as_of` filter. A historical or backtest run for date D is given strategies distilled from analyses
   of dates after D. Berkshire's `past_context` filters by resolution date (`berkshire/memory.py:103-107`,
   REQ-MEM-05) for exactly this reason. Upstream fixed the same leak in its own log (#1251, our UP-019).
5. **Frozen injection.** The skills text is read once, at `GraphSetup` construction
   (`trading_graph.py:140`), and captured in the Trader closure. That contradicts the PR's "integrated
   immediately without restart" for any graph that runs more than one ticker or date.
6. **Wrong consumer.** The critique is about `final_trade_decision`, which is the Portfolio Manager's
   output (`trading_graph.py:311`), but the lessons are injected into the Trader, not the PM.
7. **The config flag does nothing, and the dependency is mandatory.** `default_config.py:21` reads
   `ACE_ENABLED`, but the constructor defaults to `ace_enabled=True` (`trading_graph.py:58`) and never
   reads the config key. The CLI hard-codes `ace_enabled=True` (`cli/main.py:768`). The top-level
   `from tradingagents.ace import ...` (`trading_graph.py:25`, and again at `:47`) makes `ace-framework`
   a hard import for every user.
8. **Broken against the current library.** `requirements.txt` leaves `ace-framework` unpinned.
   Version 0.12.0 no longer exports `OnlineACE` or `LiteLLMClient` from `ace`, so importing
   `kayba_ace.py:14-26` fails and takes all of `tradingagents.graph` down with it. It also renamed
   `SkillManager.update_skills(reflection=...)` to `reflections=` (a tuple), which `kayba_ace.py:149-154`
   still passes the old way.
9. **Provider routing.** `LiteLLMClient(model=quick_think_llm, api_base=backend_url)`
   (`kayba_ace.py:73`) routes non-OpenAI providers wrongly: it sends a bare model name to an
   OpenAI-style base URL.
10. **Hygiene.** The engine is created twice (`trading_graph.py:110`, `:118`). Four methods are defined
    twice (`_ace_learn_from_analysis` `:292`/`:361`, `get_ace_context` `:343`/`:389`, and so on), and the
    later definition silently wins. There are bare `except:` clauses (`kayba_ace.py:197-200`), a
    `print`/traceback in place of logging, and a regex strip of an `[ACE_METADATA: ...]` tag that nothing
    emits (`trading_graph.py:313`).
11. **Prompt-injection persistence.** Web-sourced report text shapes skills that are persisted and
    re-injected into every later run for every ticker. Bot reviewers raised this (Gemini: prompt
    injection and path traversal).

Failure behaviour: the CLI wraps learning and saving in try/except (`cli/main.py:1090-1119`), so a
runtime error does not abort a run. The import-time failure in item 8 does.

## Quality and maturity

- No tests and no CI. The only reviews are bots: Copilot left 14 comments and Gemini flagged the
  duplication and injection issues. There has been no maintainer response in 9 months. The single
  human comment asked for backtest evidence and was not answered.
- The PR is built on a pre-v0.5 base (`FinancialSituationMemory`, `reflect_and_remember`, and
  `create_trader(llm, memory)`). Upstream main has since replaced this with `decision_log.py`,
  `settlement.py` and a structured `TraderProposal` Trader (`git show origin/main:tradingagents/agents/trader/trader.py`).
  It is `CONFLICTING` and would need a rewrite, not a rebase.
- Likelihood of merge: very low. If it were revived, it would change substantially.

## Value to Berkshire

- **Learning from outcomes:** negative in its current form. It replaces an outcome signal with an
  ungrounded self-grade. Berkshire's loop is already stronger: decisions are logged (REQ-MEM-01),
  settled on realised return and alpha against a regional benchmark (REQ-MEM-03), and reflected on by
  `agents/reflector.md`, with a price-target-aware judgement (REQ-MEM-08, adapted from #1087). The
  lessons are point-in-time filtered (REQ-MEM-05) and injected only into the Portfolio Manager
  (REQ-CTX-06, `berkshire/pipeline.py:322-327`). Every one of those properties is missing or broken
  in the PR.
- **Decision-time consistency:** Berkshire already checks "does the decision ignore a critical
  signal" before the order, through the bull/bear debate, the Research Manager, the risk debate and
  the PM. A post-hoc critique with no outcome adds cost without evidence.
- **The one idea with some merit:** folding many raw reflections into a small, deduplicated set of
  standing rules (a "playbook") instead of replaying the last N entries. That is not what this PR
  delivers, and doing it safely would need outcome-grounded inputs, dated rules and an `as_of` filter.
  Nothing here is ready to take.
- **Fit:** it conflicts with Claude-only models (REQ-ROLE-02), because it calls LiteLLM from inside
  the engine. It also breaks the engine/agent split, because the engine would make LLM calls itself.
  It adds a heavy third-party dependency (litellm, pydantic-ai, tau2). The Apache-2.0 licence is not
  a blocker, but nothing is worth re-implementing.

## Proposed Berkshire change

None. Berkshire's learning loop already covers the sound part of this, which is persistent lessons
fed back into the decider. It is outcome-grounded and look-ahead safe, and the PR is neither.

## Effort and risk

- Effort to adopt: none (declined).
- A hypothetical "lesson playbook" re-implemented the Berkshire way (a Reflector-written consolidation
  step at settle time, dated rules, `as_of` filtering, PM-only injection, and new REQ-MEM rows with
  tests) would be M. It carries a real risk of self-reinforcing rules, and it should not start from
  this PR.

## Open questions

- Is there any evidence, upstream or from Kayba, that ACE-style skillbooks improve trading outcomes
  beyond outcome-based reflection? Someone asked for a backtest and got no answer. Evidence of that
  kind, plus an outcome-grounded and date-filtered design, is what would justify revisiting a
  consolidated-lessons feature on its own terms.
- Should Berkshire later cap or summarise cross-ticker lessons as the log grows? That is a separate
  question from this PR, and REQ-MEM-06 rotation covers it for now.
