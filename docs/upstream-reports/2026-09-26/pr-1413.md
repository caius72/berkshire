## Summary

**Verdict: decline.** This is a multi-user SaaS layer: email signup that hands out an API key, a Stripe paywall, a quota, and a result cache shared across users. None of that fits Berkshire, which is a single-user local plugin. Its FastAPI server also has an unauthenticated path traversal that I reproduced. In the shipped Docker image, that bug exposes every user's API key and the operator's LLM and Stripe secrets. One idea is worth taking into Berkshire's own view: refuse a second dashboard job for a (ticker, date) that already has a job running (see Proposed Berkshire change).

## What it does

- **Backend** (`webapp/backend/`, FastAPI with stdlib sqlite3):
  - `POST /api/signup` takes an email and returns an `X-API-Key` (`main.py:79-84`). The key is the only credential.
  - `POST /api/analyze` runs `TradingAgentsGraph.propagate(ticker, date)` in an in-process `ThreadPoolExecutor(4)` (`jobs.py:22-50`). The client polls `GET /api/jobs/{id}` every 4 s.
  - Free users get 5 runs a month (`main.py:184-188`). A Stripe checkout and webhook switch the plan to `pro` (`billing.py:29-66`).
  - A completed (ticker, trade_date) result is reused across all users for 24 h and does not count against the quota (`database.py:225-260`, `main.py:178-182`).
  - Extra endpoints: a watchlist, profile and currency preference, API-key rotation, a live yfinance close-price chart (`charts.py`), and an FX board (`rates.py`).
  - A catch-all route serves the built SPA (`main.py:295-302`).
- **Frontend** (`webapp/frontend/`, React 18 + react-router + Vite): a landing page with pricing and FAQ, an auth modal, a dashboard with stat cards and sparklines, History, Watchlist, Profile and Exchange rates pages. The frontend shows only the final decision label and the `final_trade_decision` text. It has no per-agent progress and no per-analyst reports.
- **Deployment**: `webapp/Dockerfile`, a `webapp` profile in `docker-compose.yml`, a `[webapp]` extra in `pyproject.toml`, and a CI job that lints and builds the frontend.

The problem it solves is commercial: packaging TradingAgents as a hosted product with paid tiers (`webapp/README.md:1-30`). It does not fix any analysis failure mode.

## Soundness

### Security (server)

1. **Unauthenticated arbitrary file read (critical)**, in `webapp/backend/main.py:295-302`:
   ```python
   candidate = _FRONTEND_DIST / full_path
   if full_path and candidate.is_file():
       return FileResponse(candidate)
   ```
   `full_path` comes from `/{full_path:path}` after uvicorn percent-decodes it. Nothing resolves the path or checks that it stays inside `dist`, and the route requires no API key.
   - I rebuilt this exact route under FastAPI 0.141.1 and uvicorn 0.54.0 in a scratch venv. `curl --path-as-is` returned the planted secret file for `/../../.env`, `/%2e%2e/%2e%2e/.env`, `/..%2f..%2f.env` and `/%2e%2e%2f%2e%2e%2f.env`. It also returned the host's `/etc/hosts`. Browsers normalise `..` away, but raw clients do not.
   - The Docker image makes this worse. `webapp/Dockerfile:18,34` does `COPY . .` into the app directory. `.dockerignore:3` excludes `.env` only at the context root, and `docker-compose.yml:16` expects secrets in `webapp/.env`. So `webapp/.env` is baked into `/home/appuser/app/webapp/.env`, two levels above `dist`. That file holds the LLM provider key and `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET`.
   - The SQLite database is at `/home/appuser/.tradingagents/webapp.sqlite3`, four levels above `dist`. It stores every user's API key in plain text (`database.py:111-131`), so one request gives full account takeover. The server binds `0.0.0.0` (`Dockerfile:38`).
   - `tests/test_webapp.py:361-383` tests SPA fallback but has no traversal case.
2. **Open, unverified signup (high, cost exposure)**, `main.py:79-84`:
   - Any email string gets a working key immediately, with no ownership check and no rate limit.
   - The quota is per email, so fresh addresses (`a+1@…`, `a+2@…`) bypass the free tier. That means unbounded LLM spend on the operator's key.
   - Someone can register a victim's email first, and the victim can then never sign up.
   - A 409 on a duplicate (`main.py:81-82`) lets anyone enumerate registered emails.
3. **Quota race**: `main.py:184-189` checks `jobs_this_month` and then inserts the job, with no lock or transaction. Concurrent requests can all pass the check.
4. **No input validation on analysis parameters**:
   - `ticker` goes to the LLM pipeline and into the shared cache key after only `.upper()` (`main.py:173`). It is free text, so it can carry prompt-injection content.
   - `trade_date` is any string (`main.py:64,174`). A future date or a non-date reaches `propagate`, and `"2026-09-26 "` and `"2026-09-26"` count as different cache keys.
5. **CORS `allow_origins=["*"]`** with all methods and headers (`main.py:32-37`). The key travels in a header, not a cookie, so this is not CSRF. Still, it lets any site drive the API with a key it holds, and nothing in the design needs cross-origin access.
6. **Key storage in the browser**: when the user opts in, the key lives in `localStorage` (`useTradingApi.js:46-72`). Report text is rendered as a React text node (`ReportView.jsx:3`), so there is no XSS sink in the PR today.
7. Exception text is returned to users (`jobs.py:49`, `main.py:154`, `charts.py:35`). This is minor information leakage.

### Correctness and robustness

- **Five-tier ratings shown as three**: `utils/decision.js:1-6` classifies by substring (`buy`, `sell`, else `hold`), so Overweight and Underweight are styled as Hold. Berkshire's view already styles all five tiers plus REVIEW (`webui/src/styles.css:54-58`).
- **Orphaned jobs**: jobs run in an in-process pool (`jobs.py:22`). A restart leaves them `running` forever, with no recovery at startup. Running uvicorn with more than one worker would also split the pool across processes.
- **Cache reuse bypasses per-user configuration**: every job uses `DEFAULT_CONFIG` (`jobs.py:35`). This is consistent today, but the cache key would have to change as soon as anyone varies the analysts or depth.
- **Chart look-ahead in the UI only**: `charts.py:33` fetches `period=range_` relative to today, so a historical `trade_date` is shown next to prices from after the decision. The decisions are unaffected, but a reader can be misled.
- `@app.on_event("startup")` is deprecated in current FastAPI.

The PR's features, checked against Berkshire:

- **The cross-user result cache** has no use for a single user. Its local analogue, not re-running a complete (ticker, date), already exists as `--skip-if-complete` (`pipeline.py:187-190`) and is used by the tick.
- **Watchlist** is covered by eToro watchlists (D4).
- **Stripe, signup, quota and profile** do not transfer.
- **The price chart** is the only presentation feature Berkshire lacks. Copied as is, it would add the look-ahead display problem above. A point-in-time version could be worth it later: prices from the engine's date-clamped `data.ohlcv`, the trade date marked, and the Trader's entry, stop and target drawn in. It would matter most for reviewing a settled decision over its holding window. It is presentation only, so I do not propose it now.

Reviewing the PR against Berkshire surfaced one real Berkshire gap:

- `Api.start_job` (`berkshire/server.py:151-181`) has no guard against a second job for the same (ticker, date) while one is running. The spawned `/berkshire:analyze` calls `berkshire init` without `--checkpoint` or `--skip-if-complete`, and `init_run` then runs `shutil.rmtree(rdir)` on the existing run directory (`berkshire/pipeline.py:187-195`). A double click, or the web and TUI views both starting the same analysis, would let the second job delete the first job's in-progress run under it.
- The PR itself has the same hole: it deduplicates only completed jobs.

## Proposed Berkshire change

Do not copy anything from the PR. Take one small idea, prompted by the PR's (ticker, date) dedup:

- In `Api.start_job` (`berkshire/server.py:151`), before spawning, refuse with a 409-style error if any job in `self.jobs()` for the resolved (ticker, date) has status `running`. This mirrors the matching logic `stop_run` already uses (`server.py:218-219`). The web form and the TUI `n` dialog show the error.
- Amend **REQ-UI-06**: "A start request for a (ticker, date) whose job is still running shall be refused without spawning."
- Add a case to TST-UI-07 or a new TST-UI-25. A fake spawner and a fake running job for the same pair should give a refusal and no second spawn, while a different date should still spawn.
- Optional, same size: return a warning when a complete `state.json` already exists for the pair, since the rerun will replace it.

## Effort and risk

- Effort **S**: under 2 h, about 10 lines in `server.py`, one test, and a REQ/test-plan row.
- Risk is low. The only behaviour change is refusing a request that today corrupts a run. One edge case: a job whose process died without updating its status. `job()` already reports that as `exited` from the pid check (`server.py:192-193`), so it would not block a new start.

## Open questions
