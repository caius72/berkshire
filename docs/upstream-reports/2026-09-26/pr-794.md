## Summary

**Verdict: decline.** Twelve Data is the wrong fallback for Berkshire's Yahoo-throttling concern. It needs a
key, does not cover Berkshire's symbol universe (Yahoo-style `.DE`, `-USD` and `=F` symbols), and has no
news or insider data. Its fundamentals are not point-in-time, and the PR is stale against upstream's
refactored `dataflows/` package. UP-031 stays `watch` on its own trigger.

## What it does

The PR adds a `twelve_data` vendor to the old `dataflows/interface.py` routing table. It covers daily OHLCV
(`time_series`), 13 indicators computed on the server (`sma`, `ema`, `macd`, `bbands`, `rsi`, `atr`, `vwma`,
`mfi`), a company `profile`, and the three financial statements. News, global news and insider transactions
are stubs that raise a rate-limit error so the router moves on to the next vendor. `TWELVE_DATA_API_KEY` can
hold several comma-separated keys. Requests go to the key that has been idle longest, with at least 8 s
between calls on each key (the free tier allows 8 requests a minute). The error class subclasses
`AlphaVantageRateLimitError`, so the existing fallback loop catches it. The stated problem is that Alpha
Vantage's free tier (25 requests a day) is too tight and that yfinance's indicator and fundamentals coverage
is weak. No issue is referenced.

## Soundness

- **Stale against upstream.** `tradingagents/dataflows/interface.py` no longer exists on `origin/main`.
  Routing now lives in `tradingagents/dataflows/router.py`, vendors live under `dataflows/vendors/`, and there
  is a behaviour-based error taxonomy (`dataflows/errors.py`: `VendorRateLimitError`, `NoMarketDataError`,
  `VendorNotConfiguredError`). GitHub reports the PR as `CONFLICTING`. It needs a rewrite, not a rebase.
- **Every failure is reported as a rate limit.** In `twelve_data_common.py:91-95`, a 404 raises
  `TwelveDataRateLimitError`. `twelve_data_common.py:112-113` does the same for every other JSON error,
  including an unknown symbol or an endpoint the plan does not include. The news stubs
  (`twelve_data_news.py:1-25`) do it too. "No data" and "throttled" become the same thing, which is exactly
  the distinction upstream's later `errors.py` was written to keep.
- **A missing key aborts the run instead of falling back.** `twelve_data_common.py:29` raises a bare
  `ValueError`, which the old router did not treat as "vendor unavailable".
- **Look-ahead leaks.**
  - `get_fundamentals` (`twelve_data_fundamentals.py:6-9`) ignores `curr_date` and returns today's profile
    on a historical run.
  - `_filter_statements_by_date` (`twelve_data_fundamentals.py:44`, `:50`) keeps any period with
    `fiscal_date_ending <= curr_date`. It applies no filing lag, so a quarter that has ended but is not yet
    filed leaks into the run. Berkshire's REQ-DATA-04 uses a 45-day lag for quarters and 90 days for years.
- **The OHLCV window is never clamped locally.** `twelve_data_stock.py:18-26` trusts the API's
  `start_date`/`end_date`. Whether `end_date` is inclusive for daily bars is not checked. The helper written
  for this, `_filter_csv_by_date_range` (`twelve_data_common.py:125`), is dead code that nothing calls.
- **Throughput.** The throttle sleeps in the calling thread (`twelve_data_common.py:60`). Thirteen indicators
  on one key cost about 100 s of sleep for each Market Analyst pass.
- **Key rotation.** Several free keys are rotated to raise the effective limit. That probably breaks the
  provider's one-free-account terms and is not something Berkshire should copy.
- **What is fine.** The indicator filter is clamped to `[start, curr_date]`. The indicator cache key includes
  the date (a fix after the Gemini review). The indicator names match TradingAgents' catalogue.

## Value to Berkshire

The ledger question is whether Twelve Data is the right fallback for a scheduled daily tick over about 10
instruments on Yahoo. It is not:

- **Symbol coverage.** Berkshire's universe is written in Yahoo symbols. Examples are `SAP.DE`, `BTC-USD`, and
  `BZ=F` via `symbol_map` (REQ-IF-04, REQ-IF-10). Twelve Data uses its own symbology and exchange codes, and
  its free tier focuses on US equities, so every non-US, crypto or future instrument would need a second
  mapping layer. Futures such as the EUROOIL → `BZ=F` case are not covered.
- **Surface.** Berkshire computes indicators locally from one OHLCV frame (`berkshire/data.py:120`,
  `compute_indicator`). The server-side indicators, which are the PR's main feature, are therefore irrelevant.
  Only the OHLCV fallback would matter. News and insider data are not provided. As far as I know, the
  statements and profile endpoints are paid-tier features. Even if they were available, they are not
  point-in-time (see above), and REQ-DATA-07 and REQ-DATA-08 would have to withhold them anyway.
- **Price basis.** Berkshire reads unadjusted bars (`auto_adjust=False`, `berkshire/data.py:95-96`). A
  fallback with a different split or dividend basis would silently move the SMAs, ATR, stop levels and the
  REQ-DATA-08 split-basis check whenever the tick switched vendor. The fallback would need its own
  consistency guard.
- **Keys.** Berkshire's data decision (D3 in `docs/requirements.md`) is keyless yfinance plus eToro plus web
  search. Adding a key is an operational cost for a failure that has not been observed yet.
- **Current risk is low.**
  - The tick analyses instruments one at a time (`skills/tick/SKILL.md:25`), so Yahoo calls are spread over
    minutes of LLM time rather than arriving in bursts.
  - A Yahoo failure already degrades honestly. Tools return `DATA_UNAVAILABLE` and never a traceback
    (REQ-DATA-06). The pre-flight check treats an unreachable Yahoo as "proceed" (`berkshire/data.py:104-109`,
    REQ-IF-10), and one instrument's failure does not abort the tick (REQ-SCHED-05).
  - Berkshire is already better than this PR in two ways: its data honesty (`DATA_UNAVAILABLE` versus
    `NO_DATA_AVAILABLE`) and its point-in-time rules.

## Proposed Berkshire change

None from this PR.

If Yahoo throttling is actually observed on a tick, the cheaper fix is to reduce and retry calls before
adding a vendor:

- `ohlcv` is called several times for each instrument without caching: `check_listed`, `_history_for` from
  snapshot, indicators, ATR and valuation, and `berkshire/data.py:304`. Each `berkshire data` call is a fresh
  process.
- A small on-disk cache of the 400-day frame, keyed on symbol and trade date in the run directory, would cut
  this to about one history call per instrument per day.
- Add bounded backoff on yfinance's rate-limit exception.

If a second price source is still needed after that, prefer one that is keyless, reads Yahoo-style symbols
or maps them easily, has an explicit adjustment basis, and covers non-US listings. Twelve Data meets none of
these on the free tier.

## Effort and risk

- Adopting Twelve Data the Berkshire way: **L**. That means a vendor abstraction in `berkshire/data.py`, a
  symbol mapping, an adjustment-basis guard, key config (REQ-IF-05), and new REQ-DATA rows and tests. The risk
  is medium: mixed-basis prices feed the stop levels and the risk gate.
- The cache-plus-backoff alternative above: **S**. It would amend REQ-DATA-06 or add a REQ-DATA row, and it is
  low risk. It is not proposed until throttling is seen.

## Open questions

- Does Twelve Data's daily `time_series` treat `end_date` as inclusive, and what is its default `adjust`
  basis? Both decide whether its bars could ever be mixed with Berkshire's unadjusted Yahoo bars.
- Are there any logged Yahoo 429 / `YFRateLimitError` events from real ticks? That evidence is the trigger for
  UP-031. Without it, no fallback is warranted.
- Could the eToro MCP's candle data serve as a keyless OHLCV fallback? It is already a Berkshire dependency,
  but it is reachable only from the Claude side, not from the Python engine, so this is not established.
