# PR #1281: Make debate and analyst prompts cache-friendly — measured 4.3x prompt cache hit rate (#750)

Head `5ed37446cffb` · author yashmyeole · opened 2026-08-31, not updated since · 9 files, +121/−46 · mergeable: CONFLICTING · no CI run, no reviews, no comments

## Summary

**Verdict: decline.** Berkshire already has the structure this PR works towards: a static persona in
the agent file (the system prompt) and volatile context in a per-step prompt file. The PR's other gain,
debaters sharing a prefix with each other, cannot happen through Claude Code subagents. Each role has
its own system prompt and tool set, and those come before any message in the cached prefix.

## What it does

The PR only reorders prompt sections, so that provider-side *implicit* prefix caching (OpenAI's
automatic caching) can reuse earlier requests. It adds no caching layer.

- **Debaters** (bull/bear and the three risk debaters). The shared block (instrument context, the four
  analyst reports, the trader's decision for the risk debate, then the append-only debate history)
  moves to the start of the prompt. The role instructions and the opponent's last argument move to the
  end. Upstream sends each debate turn as one user string (`llm.invoke(prompt)`) with no role-specific
  system message, so every turn now extends the previous turn's prefix, including the other speaker's.
- **Analysts.** `Today's date is … {instrument_context}` moves from the middle of the system template
  to after `{system_message}`. The analyst prefix then stays the same across dates and tickers, which
  helps back-to-back runs and backtests.

It covers the prompt-construction half of issue #750 ("0% prompt cache hit rate"). The author reports
3 matched before/after pairs on gpt-5.4-mini: mean hit rate 7.5% → 32.4%, with the gain on the second
speaker of each debate.

## Soundness

- **The mechanism is correct for debates.** History is append-only (`history + "\n" + argument`,
  `bear_researcher.py` on main), and the leading block is byte-identical between bull and bear. The PR
  also adds the missing blank line after `Resources available:` in `bull_researcher.py` to make it so.
  It is also identical across the three risk debaters. So turn *n+1* shares turn *n*'s prefix up to
  the end of the history as it was at turn *n*. The measured effect (the second speaker going from
  0 to ~6.9k cached tokens) is what this predicts.
- **The PR is stale against main.** On main the risk debaters now also inject `{portfolio_context}`
  and use `report_or_absent` / `opponent_argument_or_opening`
  (`tradingagents/agents/risk_mgmt/neutral_debator.py` on main, ~lines 18–40). None of this is in the
  PR's hunks, so a rebase has to decide where `portfolio_context` goes. It belongs in the shared block,
  because it is identical across debaters.
- **The analyst claim is weak for sentiment.** Main's sentiment `system_message` interpolates `{ticker}`
  and the `{start_date}`–`{end_date}` window (`sentiment_analyst.py:70-72`, `:131` on main). Moving the
  date sentence after it therefore does not make that prefix stable across tickers or dates. The PR also
  concedes that the analysts' first calls are below the cacheable minimum.
- **"Wording unchanged" is not quite true.** Some phrases change ("the provided research" becomes
  "the research and data provided above"; the risk debaters' "Incorporate insights from the following
  sources" becomes "…from the sources above"). The trader decision is no longer embedded mid-instruction.
  These changes are harmless, but not zero.
- **Behaviour.** Role instructions now come after roughly 10k tokens of context. For Claude this matches
  the long-context guidance (documents first, the ask last) and is more likely to help than hurt.
  Upstream measured cost only, not decision quality. The opponent's last argument now appears twice,
  far apart: once at the end of history and once after the instructions. It was already duplicated
  before, but the two copies used to sit next to each other.
- **No point-in-time or look-ahead impact.** Only the order of the same content changes.

## Quality and maturity

There are no tests, and no CI has run (probably a first-time-contributor approval gate). There are no
reviews or maintainer response, the branch conflicts with main, and it has not been updated for four
weeks. The measurements come from the author's own tool (`tokenaudit`), with n=3 on one model: honest
about threats to validity, but also a showcase for that tool. It competes with **#878** for the same
issue. #878 is by CadeYu, who claimed #750, and is the more complete candidate: it splits static
instructions into a `SystemMessage` and dynamic context into the human message for all 13 roles,
including the trader and managers. It adds Anthropic `cache_control: ephemeral` on the static system
block, has 6 new test files, green CI, a rebase onto v0.4.2 on 2026-09-13, and an automated review with
fixes (the structured-output cache it adds never hits on a normal run; the sentiment prompt lost its
quantitative heuristics). The maintainers are more likely to take #878, or a mix, than #1281 as it stands.

**#878 against #1281.** #878 optimises the *per-role* prefix (static instructions first, cached across
turns and runs of the same role), and adds explicit Anthropic breakpoints. #1281 optimises the
*cross-role* prefix inside a debate (shared evidence first). They can be combined. Upstream's biggest
gain is #1281's cross-speaker reuse, because upstream debaters have no per-role system prompt.

## Value to Berkshire

This is provider cost plumbing. It does not affect decision quality, grounding, or risk control. What
matters is how caching works for a Claude Code subagent:

- **What the cached prefix is.** A subagent call is a Messages API request whose prefix order is
  tools → system → messages. Claude Code sets the cache breakpoints itself. The system prompt is the
  agent file body (`agents/*.md`) plus Claude Code's subagent preamble and environment block. The tool
  list differs by role (`Read, Write`; `Bash, Read, Write`; plus `WebSearch, WebFetch`), and the model
  can differ too (sonnet or opus, REQ-ROLE-02). A cache hit needs the same model and a byte-identical
  prefix.
- **What Berkshire already gets for free.** It has #878's idea: static persona in the system prompt,
  volatile context later. The persona and tool prefix of a role is reused whenever that role runs again
  within the cache TTL: the next ticker in a `/loop` tick (D4 covers holdings plus a watchlist), or the
  next date in a backtest. Inside one subagent, each tool-loop turn reuses the previous turns, so an
  analyst's repeated `berkshire data` calls are already cheap. The volatile values the PR moves out of
  the analyst system prompt (date, instrument) are already outside Berkshire's system prompt
  (`berkshire/pipeline.py:276`).
- **What Berkshire cannot get, and why.** #1281's cross-speaker reuse needs bull and bear to share a
  prefix. In Berkshire their system prompts and tools differ, and those come first, so the shared
  prefix ends before the reports. The dynamic context also arrives as a `Read` tool result, after a task
  message and a `Read` call that name step-specific paths (`skills/analyze/pipeline-loop.md:19-24`,
  `agents/bull-researcher.md:21`). So even the same role's next turn (bull_1 → bull_2) cannot reuse the
  reports block. With the default `max_debate_rounds: 1` (`berkshire/config.py:16`), each debater
  speaks only once per run anyway.
- **Prompt order.** `build_prompt` already puts the evidence first and the ask last for the debaters
  (`berkshire/pipeline.py:289-293` bull/bear, `:313-320` risk; the only thing before the reports is the
  trader's decision). The role instructions live in the system prompt. The ordering benefit is already
  there.

**Which idea fits.** #878's split (static role text as a system message, run context as the user
turn,
Anthropic breakpoint on the static part) is the one that matches Berkshire. Berkshire already has it by
construction, and Claude Code handles the breakpoints. #1281's reordering has nothing left to gain in
Berkshire.

## Proposed Berkshire change

None. Getting cross-role reuse would mean inlining the prompt text into the Agent call and giving all
debaters one shared persona. That breaks the agent-file persona design (D1, REQ-ROLE-01/05). It also
breaks the rule that the dispatcher never reads reports into its own context
(`skills/analyze/pipeline-loop.md:4-6`), and the saving is small at one debate round.

## Open questions

- Is caching actually hitting across tickers in a tick? The cache TTL (5 min by default) against the
  time between the same role's calls in a multi-ticker tick decides whether the persona and tool prefix
  is reused. You can check this without code changes: read `cache_read_input_tokens` in the subagent
  transcripts of a finished tick. Act only if that shows a large, avoidable miss.
- If upstream merges #878, check its sentiment-prompt rewrite. The automated review says it dropped the
  quantitative heuristics, and that would be a persona regression for REQ-ROLE-05 if copied.
