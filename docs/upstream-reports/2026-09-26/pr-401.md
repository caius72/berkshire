## Summary

**Verdict: decline.** Berkshire already chooses the model for each step deterministically (deep model for
the two judges, quick model for the rest, passed per step). Most of what the PR adds is multi-provider
plumbing, which D1 rules out. The one part that would carry over, a per-role override map, is not needed
yet, and the PR's version has regressions: by default it moves the judges to the quick model, and it
silently ignores the old config keys.

## What it does

The PR replaces the fixed `llm_provider` / `deep_think_llm` / `quick_think_llm` / `backend_url` config with
`llm_routing = {"default": {provider, model, base_url}, "roles": {<role>: {...} | None}}`
(`tradingagents/default_config.py:13-35` at head). `TradingAgentsGraph.__init__` loops over a hard-coded
list of 12 roles and builds one LLM client for each. It uses the role's override if there is one, and
`default` otherwise (`tradingagents/graph/trading_graph.py:74-118`). `GraphSetup` then gives each node
`role_llms[role]` in place of the quick/deep pair (`tradingagents/graph/setup.py:35-38, 79-103`).
The CLI gets a "single" or "stage" routing mode (`cli/main.py:535-633`), and the saved and displayed
reports label each section with its provider and model (`cli/main.py:674-900`).

The problem it addresses: upstream builds both clients from one `config["llm_provider"]`
(`origin/main:tradingagents/graph/trading_graph.py:75-89`), so one run cannot mix native providers,
for example Anthropic for the judges and a local endpoint for the analysts. The one substantive comment
(pippo73, 2026-08-19) gives field evidence. Its payoff is hardware placement: quick roles on a local GPU,
the judges in the cloud. It also observes that small analyst models made unit and currency errors, which
the deep judge then reasoned over faithfully.

## Soundness

Concrete problems at head `e5690d0`:

1. **Judges downgraded by default.** The only default model is `gpt-5-mini` (`tradingagents/default_config.py:16`),
   and every role override is `None`. The Research Manager and the Risk Judge / Portfolio Manager therefore
   run on the quick model. Before this PR they ran on `deep_think_llm`. This is a silent quality regression
   that affects every user who does not configure routing.
2. **Backward compatibility broken, not preserved.** The PR says existing workflows continue to work, but
   `deep_think_llm` / `quick_think_llm` are no longer read anywhere. `main.py:11-12` at head still sets them,
   and they are ignored without a warning. Any user config that uses the old keys is silently dropped, and
   the run falls back to `llm_routing.default`.
3. **Utility LLMs reassigned by accident.** `Reflector` now uses the trader's LLM, and `SignalProcessor` uses
   the portfolio manager's LLM (`tradingagents/graph/trading_graph.py:147-148`). Before, both used the quick LLM.
   Neither role is configurable. Reflection quality now depends on whatever the user picked for the Trader.
4. **Stage mode cannot separate debaters from their judge.** In stage mode, bull, bear and research_manager
   share one model (`cli/main.py:595, 603-604`). The deep/quick split inside the research team, which is the
   design the paper relies on, cannot be expressed in the CLI. The stage defaults also mark the Trader and the
   risk debaters as "deep" (`cli/main.py:596-597`), which contradicts upstream's own tiering. In stage mode every
   role is overridden, so the "Default LLM" prompt at `cli/main.py:585` has no effect.
5. **One client per role.** Twelve clients are built even when all twelve share a config
   (`tradingagents/graph/trading_graph.py:99-118`). This is harmless but wasteful, and callbacks are attached twelve times.
6. **Noise.** The diff removes unrelated comments and docstrings, and drops the trailing newlines in
   `default_config.py` and `setup.py`.

Point-in-time and look-ahead safety are not affected, because the PR touches only model selection. If a
role override is missing a key, the failure is an uncaught `KeyError` at graph construction. That is loud, so it is acceptable.

## Value to Berkshire

Berkshire already has what this PR is reaching for, as far as Claude-only use goes:

- The model is chosen per step by the deterministic engine. `berkshire/pipeline.py:29` defines
  `DEEP_AGENTS = ("research-manager", "portfolio-manager")`, and `berkshire/pipeline.py:230` puts the resolved model on every
  step the skill hands to the Agent tool. The reflector gets the quick model explicitly (`berkshire/cli.py:183`).
  `berkshire/config.py:13-14`, `BERKSHIRE_*_THINK_LLM` env vars (`berkshire/config.py:62-63`), and
  `--deep-model` / `--quick-model` flags make it configurable. TST-ROLE-02 tests it (`tests/test_pipeline.py:103`).
- The models used are persisted in the run's `state.json` (`config.deep_think_llm` / `quick_think_llm`,
  `berkshire/pipeline.py:202-204`), so the PR's "label each section with its model" transparency can already be derived.
- Berkshire does not have the PR's regressions: the judges keep the deep model by default, and the old keys remain the API.

The only thing that would transfer is a per-role override map, for example `role_models: {"market": "opus"}`.
The field evidence that analysts are the accuracy bottleneck is the best argument for it. Berkshire's
answer to that failure mode is grounding rather than a bigger model: the verified snapshot (REQ-DATA-02),
the exact-ticker identity (REQ-CTX-01), and analysts that cite numbers from tool output. A user who wants
stronger analysts can already set `quick_think_llm=opus`, which also upgrades the debaters and the Trader.
That costs more but needs no new mechanism. With Claude only, the tiers are haiku, sonnet, opus and fable, and the
two-tier knob already covers the useful combinations. Hardware placement, the main payoff in the field
evidence, does not apply to Berkshire.

The PR does not improve decision quality, grounding, honesty about data, learning, tick robustness or risk
control for Berkshire. It is provider plumbing and CLI chrome.

## Proposed Berkshire change

None. Berkshire already routes Claude models per step, and a general per-role override has no demonstrated need.

If evidence ever shows that one quick-model role is the source of errors, as the reflector's lessons or backtests
could, the Berkshire-shaped change would be small (effort S). It would add an optional `role_models` dict to
`berkshire/config.py` DEFAULTS and persist it in `state.config`. `_step` in `berkshire/pipeline.py:227-233` would
resolve the model as `role_models.get(agent)`, then the deep/quick rule. Unknown role names would be rejected
before the run. REQ-ROLE-02 would be amended to say "unless overridden per role", and TST-ROLE-02 would be
extended. The judges would keep the deep model unless explicitly overridden. This avoids regression 1 above.

## Effort and risk

- Effort: S (under 2 h) if the conditional change above is ever taken. Nothing to do now.
- Risk of adopting the PR's design: a silent quality regression for the judges and silently dropped config keys.
  The Berkshire variant avoids both by keeping the two-tier rule as the default and only layering overrides on top.
