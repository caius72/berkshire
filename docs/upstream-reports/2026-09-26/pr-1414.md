# PR #1414: fix(yahoo): print the fundamentals percentages with their unit

Head `529048c94c02`, author davidalmeida90, opened 2026-09-26, +57/-2, 2 files.

## Summary

**Verdict: adapt.** Berkshire has the same bug in a smaller form. `tool_fundamentals` prints Yahoo's `dividendYield`, which is in percent, as a bare number in the same table as five fields that are fractions. It does not print `debtToEquity`, the field that caused the misreads. The fix is a one-field unit label on same-day runs, effort S.

## What it does

`get_fundamentals` in upstream prints `Ticker.info` fields as `Label: value` lines with no units (`tradingagents/dataflows/vendors/yahoo/fundamentals.py:41-70` on origin/main). Yahoo gives `dividendYield` and `debtToEquity` in percent (AAPL 0.32 means 0.32%; 78.445 means 78.4%, i.e. 0.78x). `profitMargins`, `operatingMargins`, `returnOnEquity` and `returnOnAssets` are fractions. The PR adds a unit to just those two percent fields: `Dividend Yield: 0.32%` and `Debt to Equity: 78.445% (0.78x)` (PR head `fundamentals.py:41-45, 58, 72-73`). Missing values are still left out. It adds three offline tests with a stubbed `info` (`tests/test_fundamentals_units.py`).

The failure it prevents: the LLM reads a D/E of 115.5 as 115x, or decides the figure is a vendor artifact. The PR measured this across 16 US tickers. On v0.5.2, 5 of 12 reports that mentioned D/E misread it or disputed it. With the patch, 0 of 13 did.

I checked the live scales myself (yfinance 1.7.0, 2026-09-26):

| Ticker | dividendYield | trailingAnnualDividendYield | debtToEquity | profitMargins | returnOnEquity | revenueGrowth | earningsGrowth |
|---|---|---|---|---|---|---|---|
| KO | 2.41 | 0.0236 | 115.519 | 0.28558 | 0.42054 | 0.067 | 0.169 |
| AAPL | 0.32 | 0.0031 | 78.445 | 0.27619 | 1.48751 | 0.164 | 0.287 |

`dividendYield` is in percent and `debtToEquity` is a percentage ratio. Every margin, return and growth field is a fraction.

## Soundness

- The change is correct for Yahoo's current conventions, and the numbers above confirm it. It changes nothing else, and it keeps "omit if missing" (`if v is not None`).
- **Hard-coded convention.** The `%` label assumes Yahoo keeps `dividendYield` in percent. Yahoo switched this field from a fraction to percent in early 2025. If it switches again, the label will be wrong by 100x and nothing will flag it. A cheap guard is to compare against `trailingAnnualDividendYield` (a fraction, about `dividendYield / 100`, as the table shows). The PR does not do this. It is a minor gap.
- **Non-numeric value (minor bug risk).** `debt_to_equity / 100` (PR head `fundamentals.py:73`) raises `TypeError` if Yahoo ever returns a non-numeric value. yfinance has returned the string `"Infinity"` for other ratio fields. The broad `except Exception` in the same function (origin/main `fundamentals.py:~87`) would turn that into `NoMarketDataError`, so the whole profile would be lost over one field. Before the patch the value was printed as it came. This is unlikely, but the patch makes that failure worse.
- **Point-in-time.** Nothing changes. The patch is downstream of the existing `withhold_live_profile` guard (origin/main `fundamentals.py:31-33`), so on past dates the fields are still withheld.
- **Definition caveat.** As the PR notes, Yahoo's "total debt" includes more than balance-sheet borrowings (MSFT 29.1% against 12.8%). The label fixes the unit, not the definition.

## Quality and maturity

- Small, focused diff with offline tests (unit present, fractions unchanged, missing fields omitted). All six CI checks pass (py3.10-3.13, clean-install smoke, strict ruff). Mergeable.
- Opened today, with no reviews or maintainer comments yet. The evidence is unusually strong: a measured before/after on 16 tickers, with the reports quoted.
- Likely to merge largely as is. The only probable change is reviewers asking for a numeric guard or wanting the fields converted to fractions instead of labelled.

## Value to Berkshire

Berkshire counterpart: `berkshire/data.py:240-265` (`_FUNDAMENTAL_FIELDS`, `tool_fundamentals`). It prints `| <yahoo key> | <raw value> |` rows. On past dates it shows identity only (REQ-DATA-07, `data.py:254-255`). So the unit problem exists only on same-day runs, which are exactly the scheduled tick runs that can queue orders.

Here is which fields Berkshire prints and their scale:

| Field | Scale | Ambiguous? |
|---|---|---|
| `dividendYield` | percent (KO 2.41 = 2.41%) | **Yes.** It sits beside fractions, and a reader could take 2.41 as 241% or 2.41 as a fraction. |
| `profitMargins`, `operatingMargins`, `returnOnEquity` | fraction | No, these are the norm in the table. They would only be ambiguous if a reader assumed percent (AAPL ROE 1.4875 is 148.75%). |
| `revenueGrowth`, `earningsGrowth` | fraction | No, same as above. |
| `debtToEquity` | percent | **Not printed.** Berkshire prints `totalDebt` and `totalCash` as absolute dollars, so the misread that motivated the PR cannot happen here. |
| `trailingPE`, `forwardPE`, `pegRatio`, `priceToBook`, `beta` | multiples | No. |
| `marketCap`, `totalRevenue`, `totalDebt`, `totalCash`, `freeCashflow`, EPS, 52-week | absolute | No. |

So one of Berkshire's 23 fields is in percent, and it is printed next to five fractions. The PR's measurements found no misread dividend yield, so the practical harm is small. But the fix is almost free, and it is in line with how Berkshire handles data honestly (REQ-DATA-06/07: say what a number is, do not let the agent guess). Berkshire also has no counterpart to the PR's D/E fix, because it never prints that field. Adding `debtToEquity` is not needed: the analyst can compute leverage from `totalDebt` and the filed balance sheet (`balance_sheet`, REQ-DATA-04), which is point-in-time. That is better than Yahoo's live ratio.

Fit: this is pure data presentation, so there is no conflict with D1-D8, the engine/agent split, or the licence. It is a reimplementation of a one-line idea, not copied code.

## Proposed Berkshire change

1. In `berkshire/data.py`, next to `_FUNDAMENTAL_FIELDS` (around line 240), add `_PERCENT_FIELDS = {"dividendYield"}`. In the row builder (`data.py:256`), render those values as `f"{v}%"` when the value is numeric. The same path should state that the other ratios are fractions, either through a short footer line under the table on same-day runs ("Margins, returns and growth are fractions (0.27 = 27%); dividendYield is in percent.") or through inline `%` rendering. The footer is the smaller diff and covers all five fraction fields.
2. Optional hardening, in line with the soundness note: if `trailingAnnualDividendYield` is present and `dividendYield` is not about 100x it, print it bare with "(unit unverified)" rather than claim `%`. Skip this unless we want to guard against Yahoo switching conventions again.
3. Requirements: add **REQ-DATA-11** (S): "Profile values whose unit differs from their neighbours shall carry the unit in tool output; the table shall state that ratio fields are fractions." Add **TST-DATA-16** to `docs/test-plan.md` and a test in `tests/test_data.py` next to `test_fundamentals_withheld_on_past_dates` (`tests/test_data.py:143`). It stubs `info` with `dividendYield=2.41, profitMargins=0.28`, asserts `2.41%` on a same-day run, asserts the fraction values are unchanged, and asserts that a missing `dividendYield` produces no row. The traceability check (`tests/test_traceability.py`) makes the new REQ/TST rows mandatory.
4. No persona change is needed, although one clause in `agents/fundamentals-analyst.md:12` ("profile ratios are fractions unless marked %") would reinforce the point cheaply.

## Effort and risk

Effort **S** (about 30 minutes): one file of code, one test, and two doc rows. The risk is very low. Past-dated runs are unaffected because identity-only output skips these fields. The only behaviour change is the text of one row and a footer on same-day runs.

## Open questions

- Should Berkshire convert `dividendYield` to a fraction (÷100) so the whole table uses one scale, rather than labelling it? Labelling keeps Yahoo's number recognisable. Converting is more uniform but hides the source value. I recommend labelling.
- Should upstream add a numeric guard on `debtToEquity / 100`? It is worth a review comment on the PR. It does not affect Berkshire, which does not print that field.
- The ETF profile tool (REQ-DATA-10) prints no yield fields today (`grep -i yield berkshire/data.py` finds only `_FUNDAMENTAL_FIELDS`). If a fund yield is ever added, it needs the same unit check.
