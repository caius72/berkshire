# PR #1136: Anthropic prompt caching and token buffer for Claude 5

Upstream: TauricResearch/TradingAgents#1136, by Matt2454, head `fbbb727423c6`, opened 2026-07-11, last updated 2026-07-11.
Scope: +140/-0 across `tradingagents/llm_clients/anthropic_client.py`, `tests/test_anthropic_effort.py`, `tests/test_temperature_config.py` and an unrelated `.vscode/settings.json`.

## Summary

**Verdict: decline.** The caching half was already declined with #1281. The "token buffer" half fails on its own terms: with current `langchain-anthropic` it lowers the output cap from the model default of 128,000 tokens to 8,192–24,576, which makes truncation more likely. It is also provider plumbing that Claude Code owns for Berkshire.

## What it does

- **Prompt caching.** `NormalizedChatAnthropic._get_request_payload` is overridden (PR `anthropic_client.py:130-132`) to pass every request through `_apply_prompt_caching` (PR `anthropic_client.py:88-116`). That function deep-copies the payload and adds `cache_control: {"type": "ephemeral"}` in two places: it wraps a string `system` into one text block and marks it, or it marks the last dict block of a list `system`; and it marks the last tool definition. Conversation messages are never marked.
- **Token buffer.** `_resolve_anthropic_max_tokens` (PR `anthropic_client.py:52-80`) applies when `anthropic_effort` is set, the model accepts effort, and the caller gave no `max_tokens`. It then sets `max_tokens` from a family × effort table (PR `anthropic_client.py:19-23`): opus/sonnet 8192/12288/16384, fable (and mythos, mapped to fable) 12288/16384/24576. `get_llm` writes the result into the ChatAnthropic kwargs (PR `anthropic_client.py:156-162`).
- **Problem claimed:** repeated prompt processing in long loops, and Claude 5 reasoning that uses up a small default completion budget. No issue is referenced.

## Soundness

- **The "floor" is a ceiling (concrete bug).** Upstream has no lockfile and pins only `langchain-anthropic>=0.3.15` (upstream `pyproject.toml:13`), so a fresh install gets the current release (1.7.4). In that release `ChatAnthropic.set_default_max_tokens` defaults `max_tokens` to the model profile's `max_output_tokens` (langchain-anthropic `chat_models.py:1643-1653`), which is 128,000 for `claude-sonnet-5`, `claude-fable-5`, `claude-opus-5` and `claude-opus-5-5` (`langchain_anthropic/data/_profiles.py`). I ran the PR head in a scratch environment to check:

  | model, effort | PR `max_tokens` | main (library default) |
  |---|---|---|
  | claude-sonnet-5, high | 16384 | 128000 |
  | claude-fable-5, high | 24576 | 128000 |
  | claude-opus-5-5, low | 8192 | 128000 |
  | claude-sonnet-5, no effort | 128000 | 128000 |

  So when a user turns effort on, the PR cuts the budget that thinking and the report share by 5–16×. That is the truncation it claims to prevent. The table only helps on very old `langchain-anthropic` releases that had a 1024 default. `max_tokens` is a cap, not a reservation, so the library default costs nothing when it goes unused.
- **The PR's own test fails at head.** Gemini's review asked for the top-level `cache_control` injection to be removed, and asked for the matching test assertion to go too. The code change was applied, but the test still asserts it (PR `tests/test_anthropic_effort.py:117`). Result: `KeyError: 'cache_control'`, 1 failed and 25 passed in `tests/test_anthropic_effort.py`.
- **Effort levels outside the table.** Only `low`/`medium`/`high` are mapped. Any other level falls through to `None` (PR `anthropic_client.py:80`) and keeps the library default. So the highest-effort calls get more room than `high` does, which is the reverse of the table's intent. This does no harm, but it shows the table is not grounded in anything.
- **Caching mechanics.** Marking `system` and the last tool is valid block-level caching. A system prompt below the model's minimum cacheable length is silently not cached, so the cost is only the 1.25× write premium when it is cached and never reused. `_add_cache_control` inserts the shared module-level dict `_CACHE_CONTROL_EPHEMERAL` into every payload (PR `anthropic_client.py:84`). Mutating that dict downstream would alias across requests, which is latent but harmless today. Look-ahead and point-in-time safety are not affected.

## Value to Berkshire

- **Caching:** none. This matches the #1281 decision. Berkshire keeps the static persona in `agents/*.md` and the volatile context in the prompt file, and Claude Code handles caching for subagents. Berkshire never builds an Anthropic request payload.
- **Token buffer:** none. Berkshire roles are Claude Code subagents (`agents/*.md` frontmatter sets only `model`, and `maxTurns` for the tool-using analysts). They have no `max_tokens` or `effort` knob. The output budget belongs to Claude Code, as the ledger already records for UP-033 ("Provider reasoning/effort, temperature, retry and token knobs — not-applicable").
- **The failure mode the PR guards against is already covered.** A truncated role output fails safe in Berkshire:
  - An analyst with no output file hits the retry-then-stop path (REQ-ROLE-07).
  - A missing or invalid JSON block falls back to the free text (REQ-OUT-02, `berkshire/decisions.py:191`).
  - A final decision with no parseable rating becomes the non-tradeable `REVIEW`, never Hold (REQ-OUT-05).

  So Berkshire is already better placed here than upstream with or without this PR.
- **Fit:** it does not conflict with any decision. It simply does not apply under D1 (roles are subagents, not API clients) and the Claude-only, Claude Code-managed model choice.

## Proposed Berkshire change

None. Neither half has a Berkshire code path to land in. The one lesson that transfers is "do not cap output tokens below the model default", and Berkshire already follows it by not setting a cap at all.

## Effort and risk

Nothing to build. Declining costs nothing. Adopting would mean adding a max-output setting that Claude Code subagents do not expose, and a guessed table like this one would add truncation risk rather than remove it.

## Open questions

- If a future Claude Code release exposes a per-subagent `effort` or output-token setting in agent frontmatter, should the deep roles (Research Manager, Portfolio Manager) set it? That would be a separate REQ-ROLE-02 amendment, not this PR.
- Does upstream intend to keep supporting `langchain-anthropic` < 1.x? Only on those releases does the table raise the cap rather than lower it.
