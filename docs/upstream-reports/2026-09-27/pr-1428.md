# PR #1428: feat(graph): settle past decisions alongside the analysts

Head `060626ca2d13`, base `v0.5.2`, opened 2026-09-27 by Dangerboi. +73/-37 in 5 files.

## Summary

**Verdict: decline.** The change saves latency and does not change what the run learns. Berkshire
already covers most of the saving: it settles once per tick and runs the Reflector agents in
parallel. Overlapping settlement with the analysts would also break something Berkshire relies on:
the lessons are fixed in `state.json` when the run starts.

## What it does

Upstream settled a ticker's pending decisions inside `create_run_state`. That means price lookups
plus one reflection LLM call per decision, run one after another before the graph starts. It then
put `past_context` into the initial state. The PR moves both into a graph node, "Memory Log"
(`tradingagents/graph/trading_graph.py:300-311`). The node starts at START with the analysts and
joins them at Bull Researcher (`tradingagents/graph/setup.py:130-136`). Only the Portfolio Manager
reads `past_context`, so the settlement time is hidden behind the analysts. The PR measured a 12 s
saving on a 93 s run (-13%) with three pending decisions. A side effect: any entry point that runs
the graph now settles, even one that built its own state and skipped `create_run_state`.

## Soundness

- **Point-in-time (REQ-MEM-05 analogue): the lessons are unchanged.** Settlement and the lesson read
  still happen in order inside one node (`trading_graph.py:309-311`). The read still uses
  `_memory_as_of(trade_date)`, and the join puts it before the debate, so the Portfolio Manager
  always sees the post-settlement lessons. `past_context` is part of the checkpointed graph state.
  A resumed run therefore keeps the lessons from its first start. The new `memory=parallel`
  signature marker (`trading_graph.py:159`) stops a pre-PR checkpoint resuming without lessons.
  `_memory_as_of` now evaluates `datetime.now()` when the node runs rather than at state creation.
  This matters only for a run that crosses midnight, which is negligible.
- **No look-ahead added.** Settlement fetches closes up to now, as before
  (`tradingagents/memory/settlement.py:83-131`). For historical runs, the resolved-date filter
  removes lessons resolved after the trade date. The PR leaves both alone.
- **Concurrency is safe.** `run_config` is a `ContextVar` (`tradingagents/dataflows/config.py:45-51`).
  The node writes only `past_context`, and the analysts never touch the memory log.
- **Failure behaviour moves later.** Price and reflection errors fail open (`settlement.py:75`,
  `:114`). But an exception from `batch_update_with_outcomes` (`settlement.py:131`) or from
  `get_past_context`, for example a corrupt log, now fails the run after the analysts have started
  spending tokens. Before the PR it failed before any spend. Minor, but a real regression in failure
  cost.
- **The test's overlap assertion is vacuous.** `tests/test_graph_end_to_end.py:250` asserts
  `reflection_start < max(analyst_end)`. A Memory Log node that ran strictly *before* the analysts
  also satisfies this, so the "not alongside" message can never fire. The test really detects only
  that the node exists, via the `langgraph_node == "Memory Log"` filter at `:247`. A real overlap
  check needs `reflection_start < min(analyst_end)` and `reflection_end > min(analyst_start)`.
- **A comment goes stale.** `cli/run.py:214-215` still says `create_run_state` builds a "settled
  memory log, past context". The CLI also has no status row for the new node.

## Quality and maturity

The PR is small and focused. It adds one end-to-end test and removes the test for the old
behaviour. The author reports 1061 tests passing and a clean ruff run. There are no reviews, no
comments, and no CI checks reported, and it was opened today. It targets the unreleased `v0.5.2`
branch and builds on that branch's parallel-analyst join (9968bd8). GitHub reports it mergeable. It
is plausible to merge, since it has the same shape as the parallel-analyst work the maintainers
already took. The redundant `memory=parallel` marker may be dropped if it lands before 0.5.2.

## Value to Berkshire

Low. It is a latency optimisation, not a change to decision quality or learning. In Berkshire the
latency it hides is already small or amortised:

- **Tick:** step 4 runs `berkshire settle --all` once for the whole universe, with one Reflector agent
  per due decision launched in parallel (`skills/tick/SKILL.md:23-24`). Only then do the per-instrument
  runs start, one at a time (`skills/tick/SKILL.md:28-33`). The cost is one parallel Reflector wave
  per tick, against a tick of many subagent-heavy runs. Settling everything first also means every
  run sees today's *cross-ticker* lessons. Upstream settles only the same ticker per run, and so does
  this PR, so its runs cannot.
- **/berkshire:analyze:** it settles the one ticker (usually 0 or 1 due decisions) with parallel
  Reflectors, then runs `init` (`skills/analyze/SKILL.md:46-48`). The most this PR's idea could save is
  one Reflector agent's wall time, a small share of a run with 13 or more subagents.

Berkshire's ordering is also what makes the lessons correct. `berkshire init` fixes `past_context`
into `state.json` (`berkshire/pipeline.py:246`, `:254`), and the Portfolio Manager prompt reads it
from there (`berkshire/pipeline.py:370-371`). If settlement overlapped the analysts, the lessons
would already be fixed without the fresh reflections. Berkshire would then have to re-read the log
at the Portfolio Manager step or patch `state.json` after `settle --apply`. That extra step in the
skill would be one the orchestrating model can forget. If it did, lessons would go missing silently,
which is worse than the ~20-40 s saved. Upstream avoids this because its graph enforces the
ordering. Berkshire's engine/agent split puts the settle sequencing in the skill, and REQ-MEM-07
requires settling before the run starts (`docs/requirements.md:92`).

The robustness side effect ("any entry point settles") does not transfer. Berkshire has one run
entry (`berkshire init`), and every skill that calls it settles first. The inspection test
`tests/test_plugin.py:151` checks this. The point-in-time behaviour already has a test at
`tests/test_pipeline.py:204`.

## Proposed Berkshire change

None. The current order is settle (parallel Reflectors) → apply → init (lessons fixed) → run. It
already gives each run the complete, point-in-time-correct lesson set, including cross-ticker
lessons. The only thing it gives up is a latency saving that is small for Berkshire's run shape.

## Effort and risk

None to adopt. For reference, an adapt would take effort M: `init` would no longer fix the lessons,
or a `berkshire refresh-lessons RUN` step would run before the debate, and the analyze skill would
need changing and REQ-MEM-07 amending. The risk is medium: lessons missing silently if the skill
step is skipped. That cost is not justified by the saving.

## Open questions

- Would it be worth a cheap engine-side guard, so that `berkshire init` warns when the ticker has
  pending entries old enough to settle? It could use the log's dates only, with no price fetch. This
  would enforce REQ-MEM-07 in the engine rather than only in the skill text. It is independent of
  this PR, so raise it only if a run is ever seen skipping the settle step.
- If upstream merges this, does it later drop per-run settlement in favour of batch settlement, as
  Berkshire's tick does? That would be worth re-checking in the next scout.
