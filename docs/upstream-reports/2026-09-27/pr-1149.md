# PR #1149: docs(ollama): add custom Modelfile guide + example fast/accurate profiles

Head `862b0b5e5ec7`, author meticulo3366, opened 2026-07-15, last touched 2026-07-26. +144/-1, 4 files.

## Summary

**Decline.** This PR only adds docs and two Ollama Modelfiles for local-model users. Berkshire is Claude-only (D1, REQ-ROLE-02). The idea that could carry over, named fast and accurate profiles, is already covered by Berkshire's research depth and its deep/quick model split.

## What it does

- It adds `examples/ollama/Modelfile.trading-fast` (Q4, `num_ctx 8192`) and `Modelfile.trading-accurate` (Q8, `num_ctx 4096`).
- Both profiles set `temperature 0.2`, `top_p 0.9`, `repeat_penalty 1.05` and `num_predict 2048`, and both are sized for about 16 GB of VRAM.
- `examples/ollama/README.md` explains each parameter. It also shows three ways to wire the built model in: the CLI "Custom model ID", `DEFAULT_CONFIG`, and the `TRADINGAGENTS_*` env overrides. It recommends using one model for both deep and quick so Ollama does not swap weights.
- It adds one sentence to the README.
- The problem it addresses: self-hosters on small GPUs get truncated prompts, runaway generations and repetition loops when they run Ollama's default settings.

## Soundness

- **The 4k "accurate" profile is too small for TradingAgents.** An analyst turn holds the system prompt plus tool output (OHLCV and indicator dumps, news lists, statements). Debate and judge turns carry every analyst report plus the debate history. These regularly go past 4k tokens.
  - When a prompt exceeds `num_ctx`, Ollama drops the oldest tokens without warning. So `Modelfile.trading-accurate:15` means the "accurate" profile quietly loses its system prompt or early evidence on exactly the turns that matter.
  - The README's own tuning note ("Prompts truncated? Raise `num_ctx`") admits this, but the profile is still labelled "best fidelity".
- **`num_predict 2048` (both files, last line) can cut off a judge's or Portfolio Manager's output.** If that output hits the cap before its closing structured section, the structured decision is lost. Upstream then falls back to parsing free text, so the failure is quiet rather than a crash.
- **Temperature can be set in two places.** Upstream has a `temperature` config key (README "Reproducibility", origin/main `README.md:359`). When it is set, the request value overrides the Modelfile's. The guide does not mention this.
- **Model tags.** Gemini's review says `qwen3.5:9b-q*` does not exist in the Ollama library. I did not verify this. The files say the tags are examples to adapt.
- **Python example.** Gemini flagged a positional-argument `TypeError`. That is no longer an issue: the current head passes the analyst list positionally, which matches `TradingAgentsGraph.__init__(selected_analysts=..., ...)` (origin/main `tradingagents/graph/trading_graph.py:46`).
- **Look-ahead safety:** not applicable, since nothing touches data or dates.

## Value to Berkshire

None beyond ideas Berkshire already has:

- **Named fast/accurate profiles.** Berkshire already has two separate knobs:
  - Research depth: Shallow/Medium/Deep maps to 1/3/5 debate rounds (REQ-FLOW-07, `berkshire/cli.py:37`).
  - The deep/quick model split: `deep_think_llm` / `quick_think_llm` in `berkshire/config.py:13`, with `opus` on the Research Manager and Portfolio Manager and `sonnet` elsewhere (REQ-ROLE-02, `agents/portfolio-manager.md:4`).

  A preset that bundles both ("quick = sonnet/haiku + Shallow") would save typing one flag. It adds no decision quality.
- **Per-turn generation cap.** Berkshire's version is the turn bound: `maxTurns: 60` on the data analysts (`agents/market-analyst.md:6`, REQ-ROLE-07). A turn that runs out fails cleanly and gets a retry, where upstream's cap cuts the output silently. Berkshire is already better here.
- **Context size, quantization, temperature and repeat penalty.** None of these can be set from a Claude Code subagent, and Claude's context is not the limit these settings are working around.
- **One model for both roles to avoid weight swaps.** This is local-GPU plumbing. Doing it in Berkshire would contradict REQ-ROLE-02.
