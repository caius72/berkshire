# PR #1426: feat(dataflows): add akshare (Sina) market data vendor

- Author: vicfei (Fei.Chen). Opened and last updated 2026-09-27 (same day as this report).
- Head analysed: `1613d56f4688`. +470 / -76, 7 files. Closes issue #1425 (same author).
- Upstream ledger link: UP-031 (vendor routing with fallback chains, `adapted` as REQ-DATA-12).

## Summary

**Verdict: decline.** The vendor adds prices for US tickers, which yfinance already serves, and for
mainland A-shares, which eToro does not offer. It does not cover Hong Kong, Europe, crypto, indices,
commodities or FX, so it adds nothing Berkshire's users can trade. Its point-in-time guards are also weaker
than yfinance's.

## What it does

The PR adds a keyless vendor for three routed methods: `get_stock_data`, `get_indicators` and, newly routed,
`get_verified_market_snapshot`. It uses akshare's Sina Finance endpoints. A symbol that matches
`^(sh|sz|bj)\d{6}$` goes to `ak.stock_zh_a_daily`, and any other symbol goes to `ak.stock_us_daily`. Both
return forward-adjusted ("qfq") daily bars (`vendors/akshare/market.py:40`, `:74-77`). The full history is
kept in a 900 s in-process cache keyed by the lower-case symbol (`market.py:44-47`, `:66-70`, `:97-98`).
Indicators come from stockstats on that frame, and the snapshot copies the yfinance snapshot's layout. The
PR also moves the snapshot tool from a direct yfinance call to `route_to_vendor`
(`agents/tools.py:85-90`), files it under the `core_stock_apis` category (`router.py:54-59`), and hoists the
indicator catalogue to a module-level `BEST_IND_PARAMS` (`vendors/yahoo/market.py:22`). akshare stays an
optional import.

Issue #1425 describes the problem: from a Singapore data-centre IP, and commonly from mainland China,
every Yahoo endpoint returns `YFRateLimitError` for days. The market, news and sentiment analysts then all
get `NO_DATA_AVAILABLE`. Alpha Vantage's free tier (25 calls a day) does not last a single run.

## Soundness

The default is unchanged: `default_config.py` pins `core_stock_apis` to `yfinance`, so the new vendor only
runs when a user opts in. The problems below apply once it is enabled, plus one regression that does not
need it.

- **Regression: snapshot fails for Alpha Vantage users.** The snapshot is now routed through
  `core_stock_apis`, which only has `akshare` and `yfinance` implementations (`router.py:123-126`). A user
  with the documented `core_stock_apis: "alpha_vantage"` now gets
  `ValueError: Configured vendor(s) ['alpha_vantage'] not available for 'get_verified_market_snapshot'`.
  Before this PR the snapshot always used yfinance. Separately, the comment `# technical_indicators` at
  `router.py:122` sits above a method filed under `core_stock_apis`, so snapshot and indicators can come
  from different vendors.
- **Weaker point-in-time guards than the yfinance path.** Upstream's `load_ohlcv` filters to `curr_date`
  before gap filling, drops closeless trailing bars and rejects stale frames (#1021, #1150, #1201). The
  akshare path does none of this:
  - `_fetch_ohlcv` back-fills over the whole history, future rows included (`market.py:93`).
  - Indicators are computed on that full frame (`market.py:134-147`). The trailing indicators it offers do
    not look ahead, but the early rows are back-filled from later data.
  - There is no stale-row check. A suspended A-share (suspensions are common) shows a months-old row as
    the "latest verified" snapshot row, and the only warning is the printed date.
  - Nothing guards against a partial intraday bar.
- **Adjusted prices are not the traded prices.** qfq rescales past prices from today's corporate actions,
  so for a past date the "verified" close is not the price that traded then. yfinance with
  `auto_adjust=True` has the same property, so this is parity, not a new bug. Berkshire deliberately uses
  `auto_adjust=False` (`berkshire/data.py:144`).
- **Every failure is reported as missing data.** `except Exception` at `market.py:86` and `:211` turns
  network errors and Sina throttling into `NoMarketDataError`. A misconfigured install (`ak is None`,
  `:61`) also raises `NoMarketDataError`, not `VendorNotConfiguredError`. With `akshare` alone in the chain,
  the agent is told the symbol has no data when the vendor is actually down.
- **Empty Sina results blame Yahoo.** `raise_for_empty` is Yahoo's helper: it probes
  `query2.finance.yahoo.com` and raises "Yahoo Finance is unreachable" (`vendors/yahoo/ohlcv.py`). Called at
  `market.py:95`, `:117` and `:218`, it misattributes an empty Sina answer on exactly the networks where
  Yahoo is blocked.
- **The cache claim is half true.** The snapshot's `_fetch_ohlcv_raw` (`market.py:192-219`) duplicates the
  fetch and does not use the cache. So a run hits Sina at least twice per symbol, not once as the PR says.
- **Symbol coverage is narrow and silent about it.** Any symbol that is not `sh/sz/bj` plus six digits goes
  to the US endpoint (`market.py:77`). That includes `600519.SS`, `0700.HK`, `SAP.DE`, `BTC-USD`, `^GSPC`,
  `GC=F` and `EURUSD=X`, which all fail as "not recognized". Upstream's `normalize_symbol` is not applied.
- **One test fails without the optional dependency.** `test_unknown_symbol_reports_friendly_error` does not
  use the `fake_ak` fixture. It calls `monkeypatch.setattr(ak_market.ak, "stock_us_daily", boom)`
  (`tests/test_akshare_vendor.py:61-65`). Without akshare, `ak_market.ak` is `None` and `setattr` raises
  `AttributeError`, so the test fails on a stock install and in CI, where akshare is not in
  `pyproject.toml`.

## Quality and maturity

- **Tests:** five unit tests, all with a mocked akshare, covering cache hits, case-insensitive keys, the
  friendly error, A-share routing and the CSV header. Nothing tests the snapshot's cutoff, the indicator
  window, staleness or the routing regression. One test fails without akshare (see above).
- **CI and review:** no CI runs, no reviews, no comments. The PR was opened hours before this report.
- **Evidence:** the author reports a live 4-analyst run on `sz000001` whose cited figures match the snapshot.
- **Merge odds:** at least three older A-share vendor PRs are still open (#1067, #1109, #1183), so the
  maintainers have not taken a China data vendor yet. If this one merges, expect the snapshot-routing
  regression and the staleness guards to be reworked first.

**Compared with the sibling PRs.** #1067 (`stock_zh_a_hist`, Eastmoney), #1109 (Eastmoney spot and hist) and
#1183 (Eastmoney adapter with `stock_zh_a_daily` fallback, news and fund flow) all patch the old
`dataflows/interface.py`, which no longer exists on `main`. They also target A-share tickers only. #1426 is
the only one built on the current `router.py` and `vendors/` layout. It is also the only one that pitches
itself as a Yahoo-outage fallback for US tickers, since Sina serves both. It is the narrowest of the four:
prices only, no fundamentals, news or fund flow. None of the four adds a market that eToro lists.

## Value to Berkshire

- **Instruments Berkshire's users can trade.** I checked the eToro instrument lookup:
  - Mainland A-shares (`600519.SS`, `000001.SZ`, `sh600519`) are not found, and a name search for
    "Kweichow Moutai" returns nothing.
  - China exposure on eToro comes through Hong Kong lines (`0700.HK`, `9988.HK`), US ADRs (`BABA`) and ETFs
    (`FXI`). yfinance already serves all of these.
  - Sina via this PR cannot serve the `.HK` lines, and its own test uses `0700.HK` as the example of an
    unknown symbol.

  For a Berkshire universe, which is eToro holdings plus a watchlist (D4, REQ-SCHED-01), the only new
  coverage would be instruments the user cannot buy.
- **As a Yahoo-outage fallback:** it would cover US stocks only. It would leave out Europe (`.DE`, `.L`),
  crypto, ETFs outside the US, and the `^`, `=F` and `=X` symbols of REQ-FLOW-11. The risk gate's ATR
  (`latest_atr`) and settlement also read the same frame. A second vendor would mean mixing qfq-adjusted
  Sina bars with Berkshire's unadjusted Yahoo bars inside one run and one settlement series. That breaks
  the "one frame per run" consistency that REQ-DATA-12 provides.
- **Berkshire already addresses the underlying failure.** The run-dir OHLCV cache and bounded 429 backoff
  (REQ-DATA-12, `berkshire/data.py:105-154`) handle the scheduled-tick throttling Berkshire actually sees.
  Berkshire runs on the user's machine, not a data-centre IP. On price data Berkshire is already stronger
  than this PR: its frame is clamped to the trade date before indicators are computed, unadjusted, and
  shared by the tools and the gate. It declined a second vendor for the same reasons in #794.
- **The one transferable idea is already in Berkshire.** Routing the snapshot through the same source as
  the other price tools happens by construction: `tool_snapshot` reads `ohlcv()` like every other tool.

## Proposed Berkshire change

None. The PR adds no instrument eToro offers and no data quality. A second price vendor would break the
single-frame consistency behind REQ-DATA-12, REQ-DATA-02 and settlement. UP-031 stays as adapted.

## Effort and risk

- **Adopting it would cost M.** That means an optional `akshare` dependency, a Sina branch in `_fetch_ohlcv`,
  a qfq-versus-unadjusted reconciliation, an amendment to REQ-DATA-12, and tests.
- **The risk of adopting it is high.** Mixed price bases would reach the risk gate's ATR and settlement,
  and the lessons that learn from settlement.
- **Declining costs nothing.**

## Open questions

- Would a Berkshire user outside the US or EU, on a network where Yahoo is blocked (mainland China), ever
  run the plugin? If so, the answer is a separate data source for the eToro-listed `.HK` and US names, not
  Sina's A-share and US endpoints. Revisit only if such a user reports REQ-DATA-12's backoff exhausting on
  every tick.
- If upstream merges a China vendor, check whether upstream then fixes the snapshot-routing regression
  (Alpha Vantage users). Berkshire is not affected, because it has no vendor routing.
