# PR #806: Route TradingAgents through Claude Code and Codex CLIs

Head `468401c356b2`, author NagyVikt, opened 2026-05-11, last updated 2026-08-27. +1157/-5, 14 files.

## Summary

**Verdict: adapt.** The provider plumbing is of no use to Berkshire, but the PR's main difficulty (making a headless `claude -p` stay inside a known tool boundary) shows a real gap in Berkshire's own headless dashboard job. That job's tool boundary depends on the user's permission mode, it does not pre-approve the web tools the analysts need, and it loads the eToro MCP server that can place trades.

## What it does

It adds two LangChain chat models that shell out to local agent CLIs: `claude -p` (`tradingagents/llm_clients/claude_code_client.py:188-216`) and `codex exec --sandbox read-only` (`codex_client.py:187-221`). The goal is to run TradingAgents on a Claude or ChatGPT subscription instead of an API key. Each LLM call flattens the whole message list into one text prompt (`claude_code_client.py:88-111`). When tools are bound, it also asks the model to "return exactly one JSON object", either `{"content": ...}` or `{"content":"", "tool_calls":[...]}` (`:112-126`). It parses that envelope back into `AIMessage.tool_calls` (`:72-85`, `:129-147`), so data tools still run in LangGraph and Claude Code's own tools are switched off with `--tools ""` (`:196-197`).

The Codex side adds a process-wide lock around `codex exec` to avoid token-refresh races (`codex_client.py:30`, `:117`), detection of refresh-token/401 failures with `codex logout/login` guidance (`:37-60`), and an opt-in TTY pause to re-authenticate and retry once (`:87-105`). The PR also wires both providers into the factory, config, catalog and CLI picker, and adds env overrides for the command, timeout and extra args (`default_config.py:15-18`, `:98-101`).

## Soundness

- **`--tools ""` is not a sandbox.** The installed CLI's `--help` (2.1.283) says `--tools` restricts "the built-in set" only. MCP servers from user and project config, and claude.ai connectors, still load unless `--strict-mcp-config` is passed. The adapter also omits `--bare`/`--setting-sources`, so the user's CLAUDE.md, hooks and plugins are loaded into every TradingAgents LLM call, and the working directory is inherited from the Python process. The PR's claim that Claude Code's tools are disabled is therefore only true for built-in tools. A user with a brokerage MCP server configured still exposes it to every "chat model" call, and whether a call runs then depends on that user's permission mode.
- **A fenced tool call is silently lost.** After the review fix, `_extract_tool_envelope` accepts only a bare whole-string JSON object (`claude_code_client.py:78-85`). This correctly stops prose that contains JSON from being eaten. The other side is that a model which wraps its tool call in a ```json fence (common) falls through to `AIMessage(content=output)` (`:222-224`). The raw JSON request then becomes the analyst's final report, and nothing fails.
- **Cost and latency.** Every LLM turn is a cold `claude` process that re-sends the whole transcript plus Claude Code's own system prompt, so an analyst's tool loop of N calls means N process starts. System messages become plain user text ("System:\n…"), not a system prompt.
- **Failure behaviour.** A non-zero exit raises `RuntimeError` with stderr, falling back to stdout (`:211-215`), which is correct because `claude -p` often writes errors to stdout. `subprocess.TimeoutExpired` (600 s default, `:203-210`) is not caught and aborts the whole graph run with a raw traceback.
- **Look-ahead.** No effect. It changes transport, not data.
- `with_structured_output` raises `NotImplementedError` (`:176-179`), so every structured agent relies on upstream's free-text fallback.

## Value to Berkshire

The plugin as such adds nothing. Berkshire runs natively inside Claude Code, so its roles already are Claude subagents with native tool use (the D1 decision and the §7 mapping in `docs/tradingagents-analysis.md`). The JSON-envelope translation of tool calls solves a problem Berkshire does not have. Berkshire's structured output uses the last fenced ```json block plus schema validation (`berkshire/decisions.py:172-185`), so it is already immune to the greedy-JSON bug the reviewer found. The Codex lock and re-login pause are Codex-only.

The transferable lesson is the one the PR got half right: **a headless `claude -p` needs an explicit, mode-independent tool boundary.** Berkshire's dashboard job (`berkshire/server.py:178-180`) runs:

```
claude -p "/berkshire:analyze …" --allowedTools "Bash(berkshire *) Bash(date *) Read Write Agent"
```

This has three problems.

1. **`--allowedTools` pre-approves; it does not restrict.** Tools outside the list fall through to the user's permission mode. On this machine `~/.claude/settings.json` sets `defaultMode: "auto"`, so the auto classifier decides. The job starts from `$HOME` (`server.py:271-272`) with the user's MCP servers loaded, the eToro connector's `place-trade`, `place-close` and `execute-write` among them. D2 and REQ-UI-07 ("no order placed without explicit approval") currently rest on the prompt (skip step 5) and the classifier, not on the invocation. The only guard today, `"place-trade" not in argv` (`tests/test_server.py:142`), shows that the job does not grant order placement, not that it cannot place an order.
2. **Web tools are not pre-approved.** The News, Sentiment and Fundamentals analysts need WebSearch and WebFetch (`agents/news-analyst.md:5`, `agents/sentiment-analyst.md:5,12-14`, `agents/fundamentals-analyst.md:5`; REQ-ROLE-03). Neither is on the allowlist. Under `default` mode a headless run cannot answer a permission prompt, so those calls are denied. The analysts then write thin reports without failing (REQ-ROLE-07 only catches a missing output file). Under `auto` the outcome depends on the classifier. Either way, a dashboard analysis can differ in data from an interactive one without anyone noticing.
3. **The argv test cannot see any of this.** The reviewer's point 2 on #806 applies to Berkshire too: asserting flags in argv does not prove the CLI honours them.

Berkshire is already better than #806 on per-turn cost, native tool use, structured-output parsing and turn bounds (REQ-ROLE-07). It is weaker on the headless invocation itself.

## Proposed Berkshire change

In `berkshire/server.py:179-180`, make the headless job's boundary explicit:

```python
argv = ["claude", "-p", prompt, "--permission-mode", "dontAsk", "--strict-mcp-config",
        "--allowedTools", "Bash(berkshire *) Bash(date *) Read Write Agent WebSearch WebFetch"]
```

- `--permission-mode dontAsk` makes the allowlist the whole boundary, whatever the user's `defaultMode` is.
- `--strict-mcp-config`, with no `--mcp-config`, removes every MCP server, eToro included, from dashboard jobs. They never need eToro: the start form passes no `--portfolio`, and step 5 (enqueue) is skipped headless. This enforces D2 for the dashboard path through the invocation rather than the prompt, and it works whatever name the eToro connector has on a given install.
- `WebSearch WebFetch` gives the analysts in dashboard jobs the same data access they have in interactive runs (REQ-ROLE-03).

Requirements and tests:

- Amend **REQ-UI-06**: "…a headless `claude -p /berkshire:analyze …` job is started with permission mode `dontAsk`, no MCP servers, and an allowlist of the engine CLI, Read, Write, Agent, WebSearch and WebFetch…".
- Extend TST-UI-07 (`tests/test_server.py:135-142`) to assert these flags and that the allowlist contains no `mcp__` entries.
- Add a one-off manual demonstration (D) to `docs/test-plan.md`: start a job for one ticker from the dashboard, then check that the news report cites web sources and that the transcript shows no eToro tools and no permission denials.

Skipped:

- A wall-clock timeout on the job. `maxTurns` bounds the looping analysts, and REQ-UI-13 stop exists.
- `--no-session-persistence`. The transcript is the only debugging aid for a failed headless job.

## Effort and risk

Effort **S** (about 1 h): one argv line, one test amendment, one REQ edit, one manual check.

The risk is that `dontAsk` denies a tool the skill or a subagent quietly relies on today. The allowlist above covers everything `skills/analyze/SKILL.md` and `agents/*.md` declare, but a live run is the only proof, hence the D check. `--strict-mcp-config` should be confirmed to also drop claude.ai connectors (`mcp__claude_ai_*`), not only file-configured servers. If it does not, add `--disallowedTools mcp__claude_ai_eToro`.

## Open questions

- Does `--strict-mcp-config` drop claude.ai-hosted connectors in `-p` mode on CLI 2.1.283? This is the key fact for the eToro isolation. Verify in the demonstration.
- The only dashboard job on record (`~/.berkshire/jobs/2e094942.log`) is 0 bytes after 7 minutes, until it was stopped. With `--output-format text`, `claude -p` writes nothing until it exits, so the REQ-UI-06 "log tail" is empty for the whole run. Should the job use `--output-format json`? Its result line carries `is_error`, `subtype` (e.g. `error_max_turns`) and permission denials, which would turn "exited 0" into an honest job status and would show denied web calls directly. It is worth doing if the dashboard's job status is meant to be trusted. The run's own progress already comes from `state.json` (REQ-UI-05).
- Should `/berkshire:tick` (an interactive `/loop`, not headless) get the same explicit boundary through the skill's `allowed-tools`? It needs eToro read tools, so it cannot drop MCP. A deny list for the write tools would be the equivalent.
