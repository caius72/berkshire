# PR #941: docs: add CONTRIBUTING.md with development setup, testing, and PR guidelines

Upstream: TauricResearch/TradingAgents#941 by @zichen0116, head `ee884105efa7`, opened 2026-06-01, last activity 2026-06-30. Two files, +222/-0. Documentation only.

## Summary

**Verdict: decline.** This is a generic contributor guide for the upstream Python package, and parts of it are wrong for upstream. Berkshire's own docs already cover the same ground, and its traceability test enforces the workflow, so nothing here transfers.

## What it does

- It adds `CONTRIBUTING.md` (220 lines) with a boilerplate code of conduct, a conda plus `pip install -e '.[dev]'` setup, pytest usage with `unit`/`integration`/`smoke` markers, Conventional Commits, branch prefixes, a PR checklist, an issue-report checklist and PEP 8 style notes.
- It adds one line to `README.md` that links to the guide from the Contributing section. At the PR head this is `README.md:291`. On `origin/main` the section is now at `README.md:373-375`.
- The problem it addresses is that upstream's contributing guidance is a single sentence. It does not guard against any runtime failure mode.

## Soundness

All line numbers below refer to `CONTRIBUTING.md` at the PR head.

- **The CHANGELOG instruction is wrong.** `CONTRIBUTING.md:162` tells contributors to add an entry under `## [Unreleased]`. `CHANGELOG.md` on `origin/main` has no such section: its top entry is `## [0.5.1] — 2026-09-24`. The README (`README.md:375` on main) states the real convention, which is that maintainers credit contributions per release. The guide therefore contradicts the README it links from.
- **One setup step is outdated in the other direction.** The automated review on the PR says `pip install -e '.[dev]'` (`CONTRIBUTING.md:49`) no-ops because there is no `dev` extra. That was true at the PR's base (0.2.5) and is no longer true. `origin/main` `pyproject.toml:30-35` now defines `dev = [ruff, pytest, pytest-subtests]`, and upstream CI installs it. The line is correct today, but the review comments and the author's suggested patch are now stale.
- **The marker guidance does not match the suite.** `CONTRIBUTING.md:111-113` presents `pytest -m unit|integration|smoke` as the way to select test categories. On main, 66 of 77 test files use `unit`, one uses `integration` and none uses `smoke`, so `pytest -m smoke` selects nothing. The markers are registered (`pyproject.toml:54-58`, and again in `tests/conftest.py:31-32`), so the command runs without error but tests nothing.
- **The lint gate is missing.** Upstream CI runs `ruff check .` as a separate job ("ruff (strict, full repo)"), but the guide never mentions ruff. It says "Follow PEP 8" instead, so a contributor who follows it can still fail CI.
- **Smaller issues.**
  - The guide pins `python=3.13` (`:45`), while `requires-python = ">=3.10"` and CI tests 3.10 to 3.13.
  - The push example hard-codes `docs/add-contributing-guide` (`:167`).
  - "Questions?" (`:213`) is missing from the table of contents.
  - The guide lists "OpenAI, Google, Anthropic" API keys as a prerequisite, but the offline unit tests need none.
- **Look-ahead and point-in-time safety.** Not applicable. The guide says nothing about upstream's most important contributor rule, which is date-clamping and look-ahead safety for data tools (`tests/test_date_boundaries.py`, `test_fundamentals_lookahead.py`, `test_memory_pointintime.py`). That is the one thing a trading-framework contributor guide most needs.

## Value to Berkshire

- **Decision quality, grounding, data honesty, learning, tick robustness, risk control: none.** It is documentation for a different package's contributor workflow.
- **Berkshire is already better here.** The PR describes a workflow with conventions nothing enforces. Berkshire's workflow is enforced by tests:
  - `docs/requirements.md:9-11` requires a `REQ-*` id for every requirement and at least one test for each.
  - `docs/test-plan.md:3-11` requires every automated test to start its docstring with `TST-…: title [REQ-…]`, and lists the five conditions under which `tests/test_traceability.py` (`test_traceability`, `:53`) fails the build.
  - The coverage floor only ratchets up (`pyproject.toml:41`, `fail_under = 87`, REQ-CI-03).
  - The ruff version is pinned (REQ-CI-02).
  - `README.md:96-120` gives the exact local commands (`uv run --all-extras pytest --cov`, `npm test`, `uvx ruff@0.16.5 check .`), which match CI one-to-one.

  A contributor who skips a step fails CI with a message naming the gap. Conventional Commits, branch prefixes and a PEP 8 note would add nothing to that.
- **Fit.** There is no conflict with any decision (D1-D8), but none is helped either. The upstream setup (conda, pip, "an LLM provider API key") does not match Berkshire at all: Berkshire uses uv, a Claude-only plugin and an offline suite (`docs/test-plan.md` "Test environment").
- **Related observation, not caused by this PR.** Berkshire has no `CONTRIBUTING.md`, `CLAUDE.md` or `AGENTS.md`. The rule "a change = REQ row + TST row + docstring link + matrix row" is currently spread across the preambles of `requirements.md` and `test-plan.md`. That is acceptable because the traceability test enforces it. An agent-facing `AGENTS.md` pointer would be a separate, Berkshire-originated decision, not something this PR suggests or informs.
