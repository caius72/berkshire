# PR #1265: expose memory log, recursion limit, and news parameters in `_ENV_OVERRIDES`

Upstream: TauricResearch/TradingAgents#1265, by loulanyue, head `eff1d94f779b`, opened 2026-08-27, last updated 2026-09-03.
Scope: +37/-1 across `tradingagents/default_config.py`, `tradingagents/agents/utils/memory.py` and `tests/test_temperature_config.py`.

## Summary

**Verdict: decline.** This PR adds five env-var aliases for config keys. Berkshire already reads all four of the ones it has from `~/.berkshire/config.json`, and the fifth (`max_recur_limit`) is a LangGraph knob with no counterpart in Berkshire. Adding them as `BERKSHIRE_*` env vars would make no run behave differently.

**Relation to #1259:** #1259, by the same author, is a strict subset of this PR at the code level. Its three news keys (`news_article_limit`, `global_news_article_limit`, `global_news_lookback_days`) are three of the five rows added here. #1259 also carries the `.env.example` lines, and its tests sit in the right file (`tests/test_env_overrides.py`, with `isinstance(..., int)` checks). #1265 has neither. Both edit the same lines of `_ENV_OVERRIDES`, so whichever lands second conflicts. The same verdict (decline) applies to #1259.

## What it does

- It adds five rows to `_ENV_OVERRIDES` (PR `tradingagents/default_config.py:23-27`):
  - `TRADINGAGENTS_MEMORY_LOG_MAX_ENTRIES`
  - `TRADINGAGENTS_MAX_RECUR_LIMIT`
  - `TRADINGAGENTS_NEWS_ARTICLE_LIMIT`
  - `TRADINGAGENTS_GLOBAL_NEWS_ARTICLE_LIMIT`
  - `TRADINGAGENTS_GLOBAL_NEWS_LOOKBACK_DAYS`
- Upstream's `_coerce` converts a value to the type of the key's existing default (upstream `tradingagents/default_config.py:36-56`). The four keys with integer defaults are therefore coerced correctly.
- `memory_log_max_entries` defaults to `None` (upstream `default_config.py:79`), so `_coerce` returns the raw string (`default_config.py:56`). The rotation code would then compare `"25" <= 0` and raise `TypeError` (upstream `tradingagents/decision_log.py:255`). To avoid this, the PR wraps the value in `int(...)` inside the memory log constructor (PR `tradingagents/agents/utils/memory.py:26-27`). Upstream already uses this consumer-side pattern for `max_tokens` and `llm_max_retries` (`tradingagents/llm_clients/factory.py:59-86`).
- The problem it solves is convenience: unattended runs can set these values without editing Python. No issue is referenced, and there is no failure mode it guards against.

## Soundness

- **Stale path, will not apply.** The memory log was moved to `tradingagents/decision_log.py` on upstream main (commit `e7354d8`, "move the decision log to tradingagents/decision_log.py"). `tradingagents/agents/utils/memory.py` no longer exists there, and GitHub reports `CONFLICTING`. As rebased, the needed `int()` change would land at `tradingagents/decision_log.py:26`. If the `default_config.py` hunk were merged without the memory hunk, any use of `TRADINGAGENTS_MEMORY_LOG_MAX_ENTRIES` would crash at the first store or settle, at `decision_log.py:255`.
- **Late, unlabelled failure.** A bad value such as `TRADINGAGENTS_MEMORY_LOG_MAX_ENTRIES=abc`:
  - passes `_apply_env_overrides` silently, because the default is `None`;
  - raises a bare `ValueError: invalid literal for int()` only when `TradingAgentsGraph` builds the memory log (upstream `tradingagents/graph/trading_graph.py:91`);
  - produces an error that does not name the env var.

  This weakens upstream's own contract ("invalid values fail loudly at startup", `default_config.py:36-44`).
- **No range checks.** `MAX_RECUR_LIMIT=0` or negative news limits pass through unchecked. A negative `global_news_lookback_days` would move the macro-news window after the analysis date and break the point-in-time boundary. This is a look-ahead risk that the vendor code (`dataflows/vendors/yahoo/news.py:141`) does not guard. The risk already exists through the Python config dict, but an env var makes it easier to hit by accident.
- **Weak test.** The new test (PR `tests/test_temperature_config.py:86-113`) has these problems:
  - It sits in the temperature test file instead of `tests/test_env_overrides.py`, which already has the `_reload_with_env` helper.
  - It asserts `memory_log_max_entries in ("25", 25)`, which passes whether or not the value is coerced, and nothing exercises the new `int()` in the memory log.
  - It does not clear the other `TRADINGAGENTS_*` vars before reloading.
  - Its manual `importlib.reload` cleanup does not run if an assertion fails, so `DEFAULT_CONFIG` stays polluted for later tests.
- **Otherwise correct.** The four integer-default rows are correct and safe.

## Value to Berkshire

Berkshire's config has four layers: defaults, then `~/.berkshire/config.json`, then `BERKSHIRE_*` env vars, then CLI flags (`berkshire/config.py:1`, `berkshire/config.py:123-136`, REQ-IF-05). Here is where each knob from the PR stands:

| Upstream knob | Berkshire default | In `config.json` | In `BERKSHIRE_*` env | Consumer |
|---|---|---|---|---|
| `memory_log_max_entries` | `None` (`berkshire/config.py:19`) | yes | no | `berkshire/cli.py:26` into `berkshire/memory.py:61-67` (REQ-MEM-06) |
| `news_article_limit` | 20 (`config.py:27`) | yes | no | `berkshire/cli.py:145` |
| `global_news_article_limit` | 10 (`config.py:28`) | yes | no | `berkshire/data.py:766,774` |
| `global_news_lookback_days` | 7 (`config.py:29`) | yes | no | `berkshire/data.py:762` |
| `max_recur_limit` | n/a | n/a | n/a | No counterpart: routing is `pipeline.next_steps()` over a finite step list, with no graph recursion to bound |

- **Already covered.** Every knob that means anything in Berkshire can already be set without code changes, through `config.json`. `config.json` is also the natural channel for the scheduled `/loop 24h /berkshire:tick`: it lives in `BERKSHIRE_HOME` and survives across Claude Code sessions. An env var has to be exported in the shell that launched Claude Code.
- **No benefit to the listed goals.** An env alias would not improve decision quality, grounding, data honesty, learning, tick robustness or risk control.
- **Hazard if built naively.** Berkshire has the same trap as upstream: `load()` stores the raw string for a key whose default is `None` (`berkshire/config.py:132`). Adding `BERKSHIRE_MEMORY_LOG_MAX_ENTRIES` to `_ENV` without special coercion would reproduce the `TypeError` at `berkshire/memory.py:63` on the first settle of a tick.

## Proposed Berkshire change

None. The knobs this PR adds are already reachable through `~/.berkshire/config.json` (REQ-IF-05), and `max_recur_limit` has no Berkshire meaning.

A separate, optional hardening came out of this review. It is not what this PR does, and it should not be counted as adopting it. `validate()` (`berkshire/config.py:104-120`) does not check these keys, so a bad value in `config.json` fails late or silently:

- A string `"25"` for `memory_log_max_entries` crashes rotation at `berkshire/memory.py:63`.
- A negative `global_news_lookback_days` would move the global-news window start after the trade date.

The fix would be three lines in `validate()`: `memory_log_max_entries` must be `None` or an int >= 1, and the three news keys must be positive ints. It would come with one assertion in `TST-IF-05` (`tests/test_cli.py:15`). Do it only if someone actually edits these keys.

## Effort and risk

- **Adopting the PR's idea:** S (under 1 h). This means four `_ENV` rows, typed coercion for the `None`-default int key, and a test. The value is negligible, and forgetting the coercion risks breaking the tick.
- **The optional `validate()` hardening:** S (under 30 min), near-zero risk.

## Open questions

- Will the maintainer add `memory_log_max_entries` to `_ENV_OVERRIDES` himself? If he does, it would be worth checking whether he adds a typed "int or None" coercion to `_coerce`. That pattern is the only reusable idea here: Berkshire's `_coerce` has the same `None`-default gap at `berkshire/config.py:132`.
- Should Berkshire's `_ENV` stay a deliberate short list (models, rounds, benchmark, account, risk limits), or mirror every `DEFAULTS` key? Today `max_tickers_per_tick`, `queue_ttl_hours` and `underweight_close_fraction` are also `config.json`-only. That looks intended, and this PR gives no reason to change it.
