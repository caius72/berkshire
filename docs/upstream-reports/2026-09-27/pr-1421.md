# PR #1421: fix(graph): stop an analyst that keeps calling tools before it ends the run

Upstream: TauricResearch/TradingAgents#1421 by @hesam-shams, head `503bca6c92fd`, base `v0.5.2` (not `main`), opened 2026-09-27, no activity since. Six files, +90/-7. Fixes #1420, which the same author filed.

## Summary

**Verdict: adapt.** Berkshire has the same gap in a worse form: nothing limits how many turns an analyst subagent can take. A subagent that keeps calling tools does not crash a Berkshire run. It stalls the run, and it stalls an unattended tick with it. Take the idea as one `maxTurns` line in the frontmatter of each tool-using analyst. Keep Berkshire's current rule that a missing report fails the instrument, and do not take upstream's "continue without the report".

## What it does

- In the v0.5.2 branch, each analyst runs as its own subgraph that loops `agent → tools → agent` for as long as the model's last message asks for a tool (`tradingagents/graph/setup.py:42-44` on `v0.5.2`). The only thing that stops the loop is LangGraph's `recursion_limit` (`max_recur_limit`, default 100, `default_config.py:117`), which is reached after about 50 tool rounds. At that point `GraphRecursionError` escapes `propagate()` and the run ends with no decision.
- The PR turns `_tools_or_done` into a closure (`setup.py:45-61` at the PR head). The closure counts the messages in the analyst's private history that carry tool calls. Once the count passes `max_tool_rounds` (new config key, default 20, `default_config.py:120`), it routes to `END` without running the pending calls and logs a warning (`setup.py:56-58`).
- The analyst node sets its report only on a turn with no tool calls (`agents/analysts/market_analyst.py:80-83`), so a capped analyst leaves an empty report. The debaters then see the existing "not available, not an empty finding" marker (`agents/context.py:178-189`), and the run continues to a decision.
- The cap is added to `_run_signature` (`trading_graph.py:153`) and to `run_settings()` (`trading_graph.py:265`), and the default is wired in at `trading_graph.py:101`.

The failure it guards against: a model that never stops requesting tools, whether through a provider quirk, a tool result it keeps retrying, or a prompt that invites serial calls. #65 and #239 look like real-world cases, although the issue itself says that is not confirmed.

## Soundness

- **The boundary is right.** The count covers every tool-calling turn, including the current one, so `max_tool_rounds = N` runs exactly N rounds of tools and ends on turn N+1 (`tests/test_tool_loop_cap.py:20-27`). A single turn with several parallel calls (for example eight `get_indicators` calls) counts as one round, which is the correct unit.
- **No dangling-state bug.** The last AI message still holds unanswered `tool_calls` when the subgraph ends. That history is private to the subgraph, and the output schema returns only `report_key` (`setup.py:64-80`), so the dangling message never reaches the parent state or a provider.
- **The cap and the recursion limit are not checked against each other.** 20 rounds take about 41 supersteps, which is under 100. A user who lowers `max_recur_limit` below about `2 × max_tool_rounds + 1`, or raises `max_tool_rounds` past about 49, gets the old `GraphRecursionError` back without a warning. Nothing validates the pair, and nothing rejects a zero or negative cap (a cap of 0 quietly turns off every tool-using analyst).
- **The absence is not recorded honestly enough.** The only trace of a capped analyst is a `logger.warning`. The final state, the report and `run_settings()` record the cap but not that it was hit. A downstream reader sees "No market report in this run", which reads the same as an analyst that was never selected. Upstream's own honesty rule (#1176, `report_or_absent`) would argue for a marker saying the analyst was stopped.
- **It throws away work.** Everything the analyst gathered over 20 rounds is discarded. A more useful fallback would be one last model turn with tools unbound, asking for the report from what was already gathered. The PR does not attempt it.
- **Degrading has a cost in decision quality.** When the market analyst is capped, the Trader has no price structure to anchor its entry and stop, yet the run still produces a rating. Upstream accepts this trade-off: a decision on partial evidence rather than no decision.
- **Checkpoints stop resuming once.** Adding the cap to `_run_signature` means that, when `checkpoint_enabled` is on, a run checkpointed before the upgrade starts fresh after it. This is a one-off and harmless.
- **Look-ahead and point-in-time.** Not affected.

## Value to Berkshire

What bounds a runaway analyst in Berkshire today:

- **Nothing limits turns.** The analysts are Claude Code subagents with `Bash` and web tools (`agents/market-analyst.md:5`, `agents/news-analyst.md:5`, `agents/fundamentals-analyst.md:5`, `agents/sentiment-analyst.md:5`), and none of them sets `maxTurns`. The engine cannot see inside a subagent. It learns the outcome only when the dispatcher calls `berkshire submit`.
- **The stop only takes effect between steps.** `berkshire stop` and the dashboard's stop mark the run stopped, and the loop honours that at `next` and `submit` (`skills/analyze/pipeline-loop.md:13-14`, `:26`). A subagent that is still running is not interrupted. The dashboard kills only the headless jobs it spawned itself (`berkshire/server.py:213-231`).
- **Tool calls are bounded one at a time, but their number is not.** Each `berkshire data` call has its own limits: HTTP timeouts (`berkshire/data.py:682`), bounded Yahoo retries (REQ-DATA-12), and the Bash tool's own timeout. None of these limits how many calls a subagent makes.

What happens when an analyst fails or leaves no report:

- **An agent that returns without writing its file fails the run after one retry.** `berkshire submit` errors (`berkshire/cli.py:102-103`). The loop re-runs the step once, then stops and reports it (`skills/analyze/pipeline-loop.md:28-30`). An empty file is also rejected (`berkshire/pipeline.py:393-395`), and the debate does not start until every selected analyst has reported (REQ-FLOW-02). This is Berkshire's form of upstream's pre-PR behaviour: no decision for that instrument.
- **In a tick, that instrument is recorded as failed and the tick moves on** (`skills/tick/SKILL.md:29`, REQ-SCHED-05). With `--checkpoint`, the next tick resumes from the failed step. The outcome for a holding is "no order", which is the same as Hold. That is the safe side of the approval queue, so Berkshire is already sound for failures that *return*.
- **A runaway that does not return is the real gap.** The tick analyses instruments one at a time (`skills/tick/SKILL.md:25`) and runs in the user's `/loop` session. An analyst that keeps calling tools blocks every later instrument, the quotes, the gate and the notification, and spends tokens without limit. The "one failure never aborts the tick" guarantee (REQ-SCHED-05) does not hold for a failure that never ends. Upstream's per-analyst cap closes the same gap in a different runtime.

Berkshire is better than upstream in one respect: it does not turn a runaway into a silent empty report that still feeds an order. That behaviour should stay. The part that transfers is the bound, not the degrade policy.

## Proposed Berkshire change

1. Add `maxTurns: 40` to the frontmatter of the four tool-using analysts (`agents/market-analyst.md`, `agents/news-analyst.md`, `agents/fundamentals-analyst.md`, `agents/sentiment-analyst.md`). The number follows upstream's "twice the expected serial work" reasoning. The heaviest normal paths need about 10-20 turns: the Fundamentals Analyst's seven data tools plus Read and Write, the macro-drivers web branch, and the Sentiment Analyst's four sources with fallbacks. Parallel calls within one turn count once. `maxTurns` is a supported subagent field, and plugins do not ignore it (plugins ignore only `hooks`, `mcpServers` and `permissionMode`). The debate and decision roles have only Read and Write (REQ-ROLE-04) and need no cap.
2. Add a new **REQ-ROLE-07** (M, I): "Every analyst subagent with data or web tools shall declare a turn bound (`maxTurns`). An analyst that reaches it ends. If it has written no output file, the step fails through the normal no-output path (one retry, then the run stops, and a tick records the instrument as failed and continues), so a looping analyst cannot stall a run or a tick." Add a test-plan row TST-ROLE-12 and a check in `tests/test_plugin.py` (next to `test_analyst_data_access`, `:47`): each agent whose `tools` include `Bash`, `WebSearch` or `WebFetch` has a positive integer `maxTurns`.
3. In `skills/analyze/pipeline-loop.md:28`, say that an agent that stopped at its turn limit counts as failed. Keep the single retry, because a retry often succeeds. REQ-SCHED-05 stays as written; the new bound is what makes it hold for runaways.
4. Do **not** take the "continue without the report" half. If it is wanted later, it needs engine support: a `submit --absent` path, a REQ-FLOW-02 amendment, and a "stopped, not unselected" marker that reaches the decision and the approval prompt. It is a separate, M-sized decision.

## Effort and risk

- **Effort: S** (under an hour): four frontmatter lines, one requirement row, one test-plan row, one inspection test, and one sentence in the pipeline loop.
- **Risk: low.** If the cap is too tight, a legitimate but slow analyst (a web-heavy macro branch, a blocked StockTwits falling back to search) gets cut off and the instrument fails where it used to succeed. This is visible in the tick's failure table, and the fix is to raise the number. A second, smaller risk: an analyst that wrote a partial output file before it hit the cap would be accepted as a full report. The personas write the file last, so this should be rare.

## Open questions

- How does Claude Code count `maxTurns` for a subagent (assistant turns or tool calls), and what does the Agent tool return to the dispatcher when the limit is hit: an error, or the last partial text? One manual check (D) should confirm that the loop sees "no output file" and not a false `DONE`.
- Is 40 the right number? Record the actual turn counts from a few real ticks (the dashboard timeline records only characters, so this means reading the subagent transcripts) and set the cap at about twice the observed maximum.
- There is no wall-clock bound on a tick. `maxTurns` limits looping, not a single slow turn. If ticks ever hang on one tool call despite the Bash and HTTP timeouts, a tick-level deadline is the next step.
- If upstream changes the capped analyst to report "stopped" instead of an empty report, or adds a final no-tools turn that salvages a report, revisit item 4.
