## What it does

Registers `meta` as an OpenAI-compatible provider pointing at `https://api.meta.ai/v1`: a `ProviderSpec` row (`tradingagents/llm_clients/openai_client.py:227`), a `META_API_KEY` env mapping (`tradingagents/llm_clients/api_key_env.py:38`), a quick/deep model catalog entry with `muse-spark-1.3-contributor` / `muse-spark-1.3` (`tradingagents/llm_clients/model_catalog.py:222-232`), a CLI picker row (`cli/prompts.py:339`), plus `.env.example` and README lines. No new behaviour beyond routing to another endpoint; it solves "I want to run TradingAgents on Meta's models".

## Soundness

Mechanically fine: it follows the exact pattern of the neighbouring `groq`/`nvidia` entries and inherits `NormalizedChatOpenAI`. Small gaps:

- `meta` is not in `_ANY_MODEL_PROVIDERS` (`tradingagents/llm_clients/validators.py:8-11`), so a "Custom model ID" (which the catalog explicitly offers) will fail `validate_model` and trigger a warning, unlike the other hosted-compatible providers. Arguably intentional given the fixed catalog, but inconsistent with offering Custom.
- No row added to the parametrized registry test (`tests/test_provider_registry.py:28-44`), so the base URL is untested.
- The endpoint and model IDs are not verifiable from the PR; the claim of validation is the author's (and a Warp agent's) own. No tool-calling / structured-output compatibility evidence, which is what actually matters for TradingAgents' structured roles.

No point-in-time, look-ahead or data concerns: it touches no data path.
