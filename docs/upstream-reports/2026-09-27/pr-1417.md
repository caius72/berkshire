# TradingAgents PR #1417: configurable LLM request timeout

- Head: `22427a487519` · Author: Dangerboi · Opened 2026-09-26, last activity 2026-09-26
- Files: `tradingagents/llm_clients/factory.py`, `tradingagents/llm_clients/bedrock_client.py`,
  `tradingagents/default_config.py`, `tests/test_llm_timeout.py`, CHANGELOG (+84/-0)

## Summary

**Verdict: adapt.** The PR's own mechanism is a per-request timeout on the provider SDK, and
Berkshire already has one: Claude Code owns every model request. What does transfer is the idea
behind it, that a hung call must not block the work forever. Berkshire lacks that at one level,
the headless `claude -p` dashboard job. That job has no wall-clock limit. A hung job stays
`running` indefinitely, and while it does, it blocks any restart of the same ticker and date.

## What it does

It adds `llm_timeout` (env `TRADINGAGENTS_LLM_TIMEOUT`), default `None`
(`default_config.py:21`, `:100-101` at head). `build_llm_kwargs` forwards it as
`kwargs["timeout"] = float(timeout)` only when it is set (`factory.py:117-120` at head). The
OpenAI, Anthropic, Google and Azure clients already list `timeout` among the keys they pass to
the provider. That is `_PASSTHROUGH_KWARGS` in `openai_client.py:166`, `anthropic_client.py:9`
and `azure_client.py:8`, and the key loop in `google_client.py:48`, all on origin/main. So for
those four providers the PR is only config wiring. Bedrock did not pass `timeout` through, and
now it does, as `math.ceil(timeout)` (`bedrock_client.py:70-73` at head). langchain-aws turns
that value into the botocore connect and read timeouts, in the same `Config` that carries
`max_retries`.

The problem it solves: since v0.5.1 built every client through `build_llm_kwargs`, there has been
no way to set a timeout. A provider call that hangs therefore blocks the graph node, and the whole
run, for as long as the SDK default allows. With httpx that default can be several minutes, or
effectively forever on some stacks.

The same two config keys were part of the earlier PR #1074, which Berkshire declined (see
`pr-1074.md`). This PR is the smaller, timeout-only version of that part.

## Soundness

- **Correct for the common path.** It follows the existing `llm_max_retries` pattern (#1091):
  forward only when set, and treat an empty env string as unset. Tests assert that the value
  reaches `root_client.timeout` and `root_async_client.timeout` on OpenAI.
- **No validation, unlike its siblings.** `float(timeout)` at `factory.py:120` accepts `0`,
  negative values, `inf` and `nan`. `_coerce_max_retries` and `_coerce_max_tokens` in the same
  file (`factory.py:59-86` on main) reject bad values with a message that names the key.
  - `TRADINGAGENTS_LLM_TIMEOUT=0` makes every request time out immediately, and with retries
    the run fails after several wasted attempts.
  - `"abc"` raises a bare `could not convert string to float` that does not name the key.
  - On Bedrock, `math.ceil(float("inf"))` raises `OverflowError` and `math.ceil(float("nan"))`
    raises `ValueError`, inside `get_llm` rather than at startup
    (`bedrock_client.py:72` at head).

  A `_coerce_timeout` (a positive, finite float) would match the file's own convention.
- **Semantics are per attempt, not per run.** A float timeout is applied to each phase of each
  attempt: connect, read and write. For httpx, the read timeout counts the gap between bytes. The
  worst case per call is therefore about `timeout × (max_retries + 1)` plus backoff, not
  `timeout`. For non-streaming calls from reasoning models (deep_think with high effort), no
  bytes arrive until generation ends. A timeout set too low turns a slow call that would have
  succeeded into a retried and paid-for failure. The PR gives no guidance on a safe value and
  changes neither the README nor the config docs, only the CHANGELOG.
- **Test depth.** The Google test only checks the constructor attribute (`llm.timeout == 12.5`),
  not that the value reaches the HTTP layer. Bedrock uses a fake class, and the author says they
  checked it by hand against real langchain-aws. `pyproject.toml` pins `langchain-aws>=1.5.0`,
  which meets the `>=1.4.2` the PR says it needs. No test covers a bad value.
- **Point-in-time and look-ahead:** not affected. The change touches transport only.

## Value to Berkshire

**The literal change does not transfer.** Berkshire makes no provider calls of its own. Every
model request goes through Claude Code, which already bounds it. The installed CLI (2.1.283) reads
`API_TIMEOUT_MS`, which defaults to 600000 ms, plus stream first-byte and idle timeouts,
`MCP_TOOL_TIMEOUT` for the eToro MCP calls, and `BASH_DEFAULT_TIMEOUT_MS` /
`BASH_MAX_TIMEOUT_MS` for `berkshire data …`. Berkshire's own HTTP calls also carry timeouts
(`berkshire/data.py:682`, `berkshire/client.py:72`). The per-request level is covered, and a
Berkshire config key would only duplicate the harness setting.

**The idea does transfer, one level up.** REQ-ROLE-07 (`maxTurns: 60` in
`agents/market-analyst.md:6` and the other three analysts) bounds how many turns a step takes, but
not how long it runs. Taken level by level:

1. **Step (a subagent call).** The harness bounds it: 60 turns, each with a request limit of 10
   min plus retries, and a tool limit of at most 10 min. That bound is loose, hours in the
   pathological case, but it is finite. A wall-clock cap here cannot be built the Berkshire way,
   because the orchestrating Claude session cannot pre-empt its own pending Agent call. Nothing to
   add.
2. **Headless dashboard job.** This is the real gap. `Api.start_job` spawns
   `claude -p /berkshire:analyze …` in its own session (`berkshire/server.py:179-181`,
   `:269-272`). Nothing ever ends it except a human pressing Stop (REQ-UI-13,
   `server.py:213-231`). `job()` reports `running` for as long as the pid lives
   (`server.py:188-199`, `:251-258`), and the duplicate guard then refuses a fresh start for that
   ticker and date (`server.py:161-164`). So a wedged job, for example a hung MCP connection or a
   stalled stream the harness keeps retrying, holds the slot and a `claude` process until someone
   notices it. A wall-clock limit that ends the job through the existing stop path fixes this at
   little cost, and the run stays resumable with `--checkpoint`.
3. **Tick.** `/loop 24h /berkshire:tick` runs ticks one after another in one session, so a slow
   tick delays the next one but never overlaps it. Orders are also safe: gate quotes are fetched
   fresh at step 7 of `skills/tick/SKILL.md`, and queue items expire after `queue_ttl_hours`
   (`berkshire/orders.py:127`, REQ-EXE-04). The only deadline a skill can enforce is a check
   between instruments ("stop starting new instruments after N hours"). That is speculative until
   a tick actually overruns. Nothing to add now.

For decision quality this is neutral. For the robustness of unattended runs it is a small real
gain.

## Proposed Berkshire change

Add a wall-clock limit to dashboard jobs, enforced lazily and reusing the REQ-UI-13 stop path.

- `berkshire/config.py`: `job_timeout_minutes` with a default of 180. Add it to the
  positive-number validation at `config.py:112`. The default must sit well above a Deep-depth
  analysis with four analysts.
- `berkshire/server.py`, in `Api.job()`: when the computed status is `running` and
  `now - started > job_timeout_minutes`, do the following.
  - Call `self.kill(job)`.
  - Mark the run stopped with `pipeline.stop_run(state, f"timed out after {N} min")`.
  - Persist the job record with `stopped` and `timed_out: true`, and report the status as
    `timed out`.

  Do this directly, not through `Api.stop_run`, because `stop_run` calls `jobs()` → `job()` and
  would recurse. The check covers jobs from an earlier server process too: they are judged by pid,
  and `_kill_job` kills by pid. It runs whenever something lists jobs: dashboard polling, the TUI,
  and the duplicate guard in `start_job`. A job that is never observed is not reaped, and that is
  harmless, because it blocks nothing until someone tries to start the same run. Mark this with a
  `ponytail:` comment: a timer thread would be the upgrade if an unobserved hung process ever
  matters.
- Requirements: add **REQ-UI-14** (M, T): "A dashboard job still running after
  `job_timeout_minutes` shall be ended as in REQ-UI-13, with the reason 'timed out after N min'. Its
  status shows timed out, and the run resumes with `--checkpoint`." Add a cross-reference to it in
  REQ-UI-06.
- Test **TST-UI-26** in `tests/test_server.py`, using the existing fake spawner and killer:
  - backdate a job's `started` past the limit → listing jobs kills it once, marks the run stopped
    with the timeout reason, and reports `timed out`;
  - a fresh job is untouched;
  - a restart for the same ticker and date is then accepted.
- Optional, one line in the README: for unattended ticks, `API_TIMEOUT_MS` and `MCP_TOOL_TIMEOUT`
  in Claude Code settings are the per-request knobs, and Berkshire deliberately does not duplicate
  them.

Not proposed:

- an `llm_timeout` config key, which the harness already provides;
- a per-step wall clock, which cannot be pre-empted from the orchestrator;
- a tick deadline, which has no observed need;
- `--max-turns` on the headless job, because the orchestrator's turn count grows with depth and
  the wall clock covers the same failure more simply.

## Effort and risk

- **Effort: S.** About 20 lines in `server.py`, one config key, one requirement row, one test and
  the traceability rows.
- **Risk: low.** The worst case is a limit set too low, which stops a slow but healthy run. The
  run keeps its state and resumes with `--checkpoint`, so no work or order is lost. Orders are
  never involved, because jobs only analyse.
- **Licence:** there is no code to copy; the idea is re-implemented at a different layer.

## Open questions

- What default should `job_timeout_minutes` have? Measure one Deep-depth analysis with four
  analysts on the dashboard and set the limit at about 3× that; 180 min is a placeholder.
- What is `MCP_TOOL_TIMEOUT`'s effective default in the installed Claude Code? The binary clamps
  it but its constant is not obvious. If it is very large, a hung eToro MCP call in a tick (steps
  1 and 7) is the one per-call wait that is practically unbounded, and it is worth setting in the
  user's settings. That is a configuration fix, not a Berkshire code change.
- Should an eventual tick deadline be enforced between instruments (check elapsed time before
  each `berkshire init`)? Revisit only if a tick is observed running past the next trading day's
  open.
