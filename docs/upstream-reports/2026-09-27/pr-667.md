## Summary

**Verdict: adapt (idea only, small).** The Ollama check does not transfer, because Berkshire is Claude-only and has no model server to ping. The idea behind it does transfer: check the tick's external dependencies before spending work, and fail loudly with the cause. Build it into `/berkshire:tick` as a Yahoo Finance reachability probe, plus an explicit rule to abort and notify when an eToro read fails. Do not build it as a standalone `doctor` command. This keeps the #1408 decline intact: a manual command never runs under `/loop`, so it would not help the scheduled tick.

## What it does

`ollama_check.py` strips `/v1` from the configured backend URL (`ollama_check.py:16-30`). It then calls `GET /api/tags` on the Ollama server, lists the local models, and checks that `deep_think_llm` and `quick_think_llm` are among them (`ollama_check.py:68-123`). The PR hooks this in two places. A new `tradingagents check` command builds its config from `LLM_PROVIDER`, `OLLAMA_HOST`, `DEEP_THINK_LLM` and `QUICK_THINK_LLM` and exits 1 on failure. `run_analysis()` also runs the check before building the graph, as a warning only. The problem it solves: when Ollama is not running or the model is not pulled, the user gets a vague "Connection Failed" deep inside a run. This check reports the fix up front (`ollama serve`, `ollama pull <model>`).

## Soundness

The mechanism is fine for a happy-path hint, but it has concrete bugs:

- **The check can crash startup, despite claiming it never raises.** `ping_ollama` catches only `ConnectionError` and `Timeout` (`ollama_check.py:42`), although its docstring says "Never raises" (`ollama_check.py:36`). Ollama's own `OLLAMA_HOST` convention is a bare `host:port` such as `127.0.0.1:11434` or `0.0.0.0`, with no scheme. `requests` rejects that with `MissingSchema` or `InvalidSchema`, and the exception escapes the call in `run_analysis()` that is commented "warn only — never crash startup". `list_local_models` catches the broad `RequestException` (`ollama_check.py:55`), so the two functions handle errors inconsistently.
- **The model check can pass when the model is missing.** `check_model_available` does a case-insensitive substring match (`ollama_check.py:64-65`). A configured `qwen3` matches a local `qwen3-coder:30b`, and `llama3` matches `llama3.1:8b`. So the check passes in exactly the case it exists to catch. The right test normalises a bare name to `name:latest` and compares exactly.
- **`check` reads different settings from the run.** The command reads `LLM_PROVIDER`, `DEEP_THINK_LLM` and `OLLAMA_HOST`. Upstream's config override table uses `TRADINGAGENTS_LLM_PROVIDER`, `TRADINGAGENTS_DEEP_THINK_LLM` and `TRADINGAGENTS_LLM_BACKEND_URL` (`tradingagents/default_config.py:11-14` on `origin/main`). Its Ollama URL override is `OLLAMA_BASE_URL` (`tests/test_ollama_base_url.py` on `origin/main`). So `tradingagents check` can pass while the real run points at a different host or model.
- **Minor.** `/api/tags` is fetched twice, once to ping and once to list. `run_ollama_check` prints straight to its own module-level `Console`, not the CLI's one.
- **Point-in-time and look-ahead.** Not applicable. The check touches only the environment, never market data.

## Value to Berkshire

**The Ollama check itself: none.** Berkshire runs only Claude subagents inside Claude Code (D1, REQ-ROLE-02). It has no model server, no API keys and no model pull step. This is provider plumbing.

**The preflight idea, for the scheduled tick: real, but narrow.** Here is what Berkshire already covers and where the gap is:

- **Config is already covered.** `config.load` validates every setting on every `berkshire` command (`berkshire/config.py:104-134`). The tick's first command, `berkshire config`, fails loudly on a bad setting (`skills/tick/SKILL.md:13`). A separate config check would add nothing.
- **eToro connectivity is half covered.** Step 1 of the tick is an eToro MCP read (`skills/tick/SKILL.md:15-17`), so that read already acts as the probe. The gap is what happens when it fails. The skill never says, and the only notification it defines is the success one at step 10 (`skills/tick/SKILL.md:34-35`). Under `/loop 24h` with "ask the user nothing" (`skills/tick/SKILL.md:37`), a disconnected or expired eToro MCP can end the day's tick with no notification. That is a real robustness gap in unattended runs, and fixing it takes one sentence.
- **Yahoo Finance reachability is the main gap.** Each run's Yahoo checks are deliberately fail-open. The identity lookup and `require_listed` treat "unreachable" as "carry on" (`berkshire/pipeline.py:210-215`, `berkshire/pipeline.py:226-227`), and `check_listed` returns `None` for unreachable (`berkshire/data.py:157-162`). During a Yahoo outage or rate-limit spell, the tick therefore runs the full 13-role pipeline for every instrument. Every data tool returns `DATA_UNAVAILABLE` (REQ-DATA-06), and the analysts reason from web search alone. The run still ends in a rated decision that can be queued. REQ-EXE-02 still requires a human to approve each order, so this is not a safety hole. It is a waste of a tick's tokens, and it pushes poorly grounded proposals into the approval queue and the decision log, where they later feed reflection. Settlement already degrades safely on its own: entries that cannot be priced are left for the next run (`berkshire/memory.py:166-171`).

Berkshire's per-call markers (REQ-DATA-06) are already better than upstream's behaviour. What is missing is the one tick-level decision: "the price source is down, do not analyse today."

## Proposed Berkshire change

Put the check inside the tick. Do not add a `doctor` command.

1. **`berkshire universe` reports whether Yahoo is reachable.** Add `"yahoo_reachable": data.check_listed("SPY", date) is not None` to its output (`berkshire/cli.py:246-251`). This reuses the existing probe and adds no new helper. It costs one small request, which the tick needs anyway.
2. **`skills/tick/SKILL.md` gets two abort rules.**
   - Step 1: if an eToro MCP call fails (not connected, auth, error), send a PushNotification "Berkshire DATE: tick aborted, eToro unreachable: <cause>" and stop.
   - After step 5: if `yahoo_reachable` is false, settle as usual (it retries by itself), then notify "Berkshire DATE: settled N, analysis skipped, Yahoo Finance unreachable" and stop before step 6.
3. **Requirements.** Add REQ-SCHED-06 (M): "A tick shall stop before analysis, with a notification naming the cause, when the eToro portfolio or watchlist read fails or Yahoo Finance is unreachable. A failed tick is never silent." Amend REQ-SCHED-01 so that it notifies on abort as well as on completion.
4. **Tests.** TST-SCHED-06 (T) monkeypatches `data.check_listed` to return `None` and asserts that `universe` reports `yahoo_reachable: false`, and `true` when the probe returns `True` or `False`. TST-SCHED-07 (I) asserts that the tick skill names both abort rules and a notification on abort. Extend manual procedure M3 (TST-SCHED-05) with one run where the network is off.

## Effort and risk

**Effort S** (under 2 hours): one field in `cmd_universe`, two sentences in the tick skill, one REQ row, two tests and a traceability row. **Risk is low.** The probe is fail-safe in the right direction: a false "unreachable" skips one day's analysis, and settlement is unaffected. The one real risk is a Yahoo block of SPY alone while other symbols still work. That is unlikely, and it costs one skipped tick, not a bad order.

## Open questions

- **Probe symbol.** Use SPY, or the configured benchmark (`benchmark_ticker` / `benchmark_map` in `berkshire/config.py:21-22`)? SPY is the simplest. The benchmark matches settlement better for non-US books.
- **Stale data on holidays.** `is_trading_day` treats exchange holidays as "stale data, not an error" (`berkshire/cli.py:254-256`). The same probe could return the latest bar date and flag a US holiday. That is a separate, optional step.
- **Outage during a tick.** If Yahoo fails after the preflight passes, only the per-tool `DATA_UNAVAILABLE` markers remain. Should a run whose verified snapshot is `DATA_UNAVAILABLE` be marked failed rather than rated? Leave this until an outage in the middle of a tick is actually seen.
