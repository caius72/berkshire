## Summary

**Verdict: decline.** This is LangChain callback plumbing that solves an attribution problem Berkshire
does not have: each step's model is fixed by the engine, and Claude Code already records tokens per
subagent and per model. It does nothing for decision quality or tick robustness.

## What it does

The CLI's `StatsCallbackHandler` keeps global counters (LLM calls, tool calls, tokens in and out) for the
live panel (`cli/display.py:350-361` on `origin/main`). The PR adds a `by_model` dict. When a model call
starts, it stores `run_id → model name` (`cli/stats_handler.py:69-87` at head). It guesses the name from
`invocation_params`, then `serialized.kwargs`, then the class id, then `"unknown"` (`:35-59`). On
`on_llm_end` it pops that name and adds the call's `usage_metadata` tokens to the model's bucket
(`:108-132`). `get_stats()` returns the breakdown (`:152`). The goal is cost attribution when a run mixes
the deep and quick models. There is no linked issue, and no upstream code reads `by_model`: `display.py`
is unchanged, so the new data reaches only outside callers.

## Soundness

- **`_run_models` leaks entries** (the Gemini bot's two high-priority comments are right). The entry is
  popped only after the `usage_metadata` check, so a call that ends without usage returns first at
  `:108-109` and keeps its entry. The same happens on the empty-generations return at `:99-100`. The PR
  has no `on_llm_error`, so failed calls (rate limits, timeouts, which are common with retries) also keep
  theirs. Each run is one short CLI process, so the leak is small in practice. It would matter in a
  long-lived server. The fix is to pop first, then return.
- **The totals don't add up.** The top-level `llm_calls` counts starts (`:71`, `:85`). `by_model[*].llm_calls`
  counts only ends that had usage (`:130`). Their sums differ silently whenever a call fails or reports no
  usage, and the PR never says so.
- **"Attribute cost accurately" overstates it.** The buckets hold only `input_tokens` and `output_tokens`
  (`:111-112`). With Anthropic prompt caching, LangChain folds cache reads and cache writes into
  `input_tokens`, and those are priced very differently (reads at about a tenth of the base rate, writes at
  more than the base rate). Pricing the buckets therefore needs `input_token_details`, which the PR drops.
- **The fallback can give a class name as a model name.** `serialized["id"][-1]` (`:56-58`) is a class name
  such as `ChatAnthropic`. That merges every model of that class into one bucket, the problem the PR is
  meant to fix.
- There is no look-ahead or point-in-time concern. This is telemetry only, it doesn't change the graph,
  and a failed model-name lookup falls back to `"unknown"` without raising.

## Value to Berkshire

Low. The problem the PR solves, finding out at end time which model served a call, cannot arise in
Berkshire:

- **The engine assigns the model.** `pipeline._step` sets each step's model from `DEEP_AGENTS`
  (`berkshire/pipeline.py:29`, `:273-279`; REQ-ROLE-02). The dispatcher passes that model to the Agent call
  (`skills/analyze/pipeline-loop.md:17`). The model per step is already known and persisted with the step.
- **Claude Code already records usage.** Each subagent's result carries
  `<usage>total_tokens, tool_uses, duration_ms</usage>`. The session transcript stores this as
  `usage: {totalTokens, toolUses, durationMs}` for every task. Each subagent's own transcript
  (`~/.claude/projects/<proj>/<session>/subagents/agent-*.jsonl`) logs `model` and the full Anthropic
  `usage`, cache split included, on every message. That already gives per-step, per-model accounting,
  and more accurately than the PR does. Ledger row UP-033 already puts token knobs under "handled by
  Claude Code".

**Does per-step cost visibility matter for the daily tick?** Only a little. With the defaults (1 debate round
and 1 risk round, `berkshire/config.py:16-17`), a run is 12 subagent steps, 2 of them on opus. With
`max_tickers_per_tick: 10` (`:40`), a tick is about 120 steps plus the reflectors. A sampled Berkshire
subagent used about 61k tokens, mostly cached. On a Claude subscription the real risk is running out of the
usage window mid-tick, not a surprise bill, and REQ-SCHED-05 (one failure never aborts the tick) with
`--checkpoint` resume already covers that failure. A token count in the tick summary would be nice to
have, but it would not change any decision or gate. Berkshire is no worse than upstream here. Upstream's
counter is a CLI panel figure, and Berkshire gets the same numbers, split by cache, from Claude Code.

**Fit:** there is no conflict with D1 to D8, but the code does not transfer. Berkshire has no LangChain
callbacks, and the mechanism is specific to that library.

## Proposed Berkshire change

None. The one idea worth keeping: if ticks start hitting usage limits, the dispatcher could read each
Agent result's `total_tokens` and `duration_ms` and pass them to `berkshire submit RUN <id> --tokens N
--ms N` (`skills/analyze/pipeline-loop.md:26`). The engine would store them on the step and total them per
run and per model. The tick summary (`skills/tick/SKILL.md:34`) would then report the day's token count.
That is an adapt with effort S. It needs a new REQ-SCHED or REQ-RPT row and one submit test. Leave it until
there is a concrete need.

## Effort and risk

Declining costs nothing and carries no risk. The deferred option above is S (under 2 hours: one optional
CLI flag, one state field, one line in the summary, one test) with near-zero risk. It is telemetry and never
feeds routing (REQ-FLOW-08) or the gate.

## Open questions

- Is Berkshire run on a Claude subscription or on API billing? With API billing, a daily dollar figure per
  tick becomes more useful, and the deferred option should be built with cache-aware pricing, not
  input/output totals.
- Is `total_tokens` in the Agent result a documented, stable field, or an implementation detail of Claude
  Code? It should be confirmed before the engine depends on it. Reading the subagent transcripts is the
  fallback.
