## What it does

Upstream's post screening (#1376, `tradingagents/agents/post_screen.py` on main) posts each StockTwits and Reddit post to TypeSafe's System One at a hard-coded `_URL` (`post_screen.py:26` on main). It asks two typed questions (about / stance), drops the clearly off-topic posts, and puts a stance count at the head of each source's block. #1427 replaces `_URL` with `TYPESAFE_BASE_URL` (default `https://api.typesafe.ai`) plus a fixed `/v1/systemone` path (`post_screen.py:27-28,83-84` at PR head). It sends the bearer header only when `TYPESAFE_API_KEY` is set (`post_screen.py:81-82`), and it turns screening on when either variable is set (`post_screen.py:137`). The stated problem is a hard dependency on one vendor that "may not be accepting new subscriptions": users could point screening at a self-hosted or third-party System One-compatible server. No issue is referenced.

## Soundness

- **The PR body names the wrong variable.** It says `JEV_API_URL`, but the code, tests, README and `.env.example` all use `TYPESAFE_BASE_URL`, and `JEV_API_URL` appears nowhere in the tree. A reviewer who goes by the description will be misled.
- **The commented default in `.env.example` turns screening on.** `.env.example:28` shows `#TYPESAFE_BASE_URL=https://api.typesafe.ai` as if it were the default. A user who uncomments it without setting a key turns screening on (`post_screen.py:137`) and sends keyless requests to TypeSafe. Each request then fails with HTTP 401. That is not retried (`_RETRY_STATUSES`), so it becomes `TypeSafeError`, and every source prints `<Jev screening unavailable (HTTP 401)…>` on every run (`post_screen.py:162`) and logs a warning. The failure is safe (posts pass through unscreened), but it is noisy and confusing. The guard would be more honest if it compared against the default rather than testing whether the variable is set.
- **The key can go to another host.** With both variables set, the TypeSafe bearer key goes to whatever host `TYPESAFE_BASE_URL` names, plain `http://` included (`post_screen.py:81-84`). The PR intends this for compatible servers, but the key keeps its TypeSafe name and nothing warns about it. #1416 has the same issue.
- **The path is fixed.** A base URL that already ends in `/v1` produces `/v1/v1/systemone`. This is documented in the README ("the client appends `/v1/systemone`"), so it is a trap rather than a bug.
- **The labels are wrong.** Output from any server is still labelled "Screened by Jev" (`post_screen.py:153`), and `jev-latest` is still sent as the model to a non-TypeSafe server (`post_screen.py:78`). The reader of the sentiment report cannot tell which model filtered the posts. This is the same data-honesty problem as #1416.
- **The thresholds are tuned to Jev.** `_OFF_TOPIC_BELOW = 0.3` and `_STANCE_CONFIDENCE = 0.5` (`post_screen.py:38,40`) assume Jev's calibrated probabilities, and a substitute server's confidences may not match them.
- **What is correct.** Failures from the new endpoint go through the existing retry, `_answers` type check and `TypeSafeError` path. So unlike #1416's judge hook, nothing new can escape `screen()` (`post_screen.py:147-150`). Point-in-time safety is unaffected, because the same window-trimmed posts are sent. I checked out the PR head: `tests/test_post_screen.py` passes (29 tests).

## Quality and maturity

- Two tests were added (the URL follows the environment with a trailing slash stripped, and a keyless custom URL sends no `Authorization` header), and the no-key test was hardened. No test covers a key sent to a custom host or the case where the default URL is set without a key.
- No CI checks are reported, and the PR has no reviews and no comments. It is mergeable on v0.5.1 main and is minutes old.
- It competes with #1416 for the same change. The maintainers will take one of them or neither, and they may prefer a `DEFAULT_CONFIG` key over an env var. Given the body/code mismatch and the duplication, it is likely to change or to be closed in favour of #1416.

## Value to Berkshire

None that transfers.

- Berkshire has no screening endpoint to configure. UP-017 was adapted without a vendor (`docs/upstream.md:54`): the Sentiment Analyst subagent screens StockTwits, Reddit and Bluesky posts itself. It drops off-topic posts, classifies stance as bullish, bearish, neutral or unclear, and opens each source with `N of M posts on-topic: …` (`agents/sentiment-analyst.md:16`). This is REQ-ROLE-03 (`docs/requirements.md:35`).
- The PR's goal, getting screening off a single third-party vendor, is already met in Berkshire more simply, because no vendor is involved. The judge is Claude, which keeps within the Claude-only model decision and D3's data sources (`docs/requirements.md:18,20`).
- Berkshire is also better on provenance. Its count line belongs to the analyst and is reported separately from StockTwits' own user-tag split. The PR, by contrast, labels any server's output as "Jev".
- Adopting it would mean adding an HTTP vendor client and a key to the engine. That is the opposite of the UP-017 decision and the reason #1416 was declined.
