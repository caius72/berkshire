# TradingAgents PR #1121: add MiMo (Xiaomi) as an LLM provider

## Summary

**Verdict: decline.** This is provider plumbing for a non-Claude model. Berkshire is Claude-only
by decision (D1, REQ-ROLE-02), so nothing here transfers. The PR is also broken as submitted: the
provider is never registered, so selecting it fails.

## What it does

It adds a `mimo` row to the CLI provider table with the endpoint
`https://token-plan-cn.xiaomimimo.com/v1` (`cli/utils.py:362` at head). It maps `mimo` to
`MIMO_API_KEY` (`api_key_env.py:38`) and adds a `mimo-v2.5` model-catalog entry
(`model_catalog.py:181-191`). No issue is referenced. The goal is to make one more
OpenAI-compatible vendor selectable.

## Soundness

- **Selecting the provider fails at runtime.** The PR body says it registers `mimo` in
  `OPENAI_COMPATIBLE_PROVIDERS`, but `openai_client.py` is not in the diff. On upstream main, the
  factory sends every non-native provider through `is_openai_compatible`
  (`tradingagents/llm_clients/factory.py:52-54`, which reads the registry at
  `openai_client.py:212-239`). An unregistered `mimo` therefore reaches
  `raise ValueError("Unsupported LLM provider: mimo")` (`factory.py:56`). The Gemini review
  reported the same thing.
- The endpoint is a China-region "token-plan" host, and it lives only in the CLI table. Non-CLI
  users would get no default `base_url` even after the registry fix.
- No tests were added.

## Quality and maturity

- No CI checks have run. The only review is an automated one from Gemini, which flagged the
  missing registration. There is no maintainer response.
- The PR conflicts with main: `cli/utils.py` no longer exists, and `_llm_provider_table` now
  lives in `cli/prompts.py:313`.
- It has been stale since the day it was opened. It is unlikely to merge as is.

no provider registry, API-key map or model catalog that could take this. The PR has no idea beyond
the provider itself.
