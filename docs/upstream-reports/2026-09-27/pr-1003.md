# PR #1003: Add Windows launcher for setup and CLI startup

Upstream: TauricResearch/TradingAgents#1003 by hardtohard, head `ccc2fb6655d2`, opened 2026-06-08,
+154/-0 in `start_tradingagents.bat`, `scripts/start_tradingagents.ps1`, `README.md` and
`pyproject.toml`. No linked issue. Reviewed 2026-09-27.

## Summary

**Verdict: decline.** This is setup plumbing for upstream's pip/venv install. Berkshire's
`bin/berkshire` + `uv run` already covers what it does, and does it better. Against current upstream
main the launcher is also broken: it runs `cli.main analyze`, and that subcommand no longer exists.

## What it does

A `.bat` shim (`start_tradingagents.bat:4`) runs a PowerShell script with `-ExecutionPolicy Bypass`.
The script creates `.venv` with `py -3` or `python` (`scripts/start_tradingagents.ps1:41`) and checks
the venv is Python 3.10 or newer (`:65`). It copies `.env.example` to `.env` if there is no `.env`
(`:72`), then installs the project in editable mode, through `uv pip` when uv is found and pip otherwise
(`:96`). It skips the install on later runs while a marker file is newer than `pyproject.toml` (`:84`,
`:102`), then starts `python -m cli.main analyze` with optional `--checkpoint`/`--clear-checkpoints`
(`:115`). It also adds `python-dotenv>=1.1.0` to `pyproject.toml`. The problem it solves is that
first-run setup takes several steps for Windows users who are not comfortable in a shell. It is not a
correctness or decision-quality fix.

## Soundness

- **Broken on current main.** Upstream #1234 (d8eceb6, 2026-09-16) turned `analyze` into the Typer
  app callback (`cli/main.py:30-31` on origin/main, `@app.callback(invoke_without_command=True)`). The
  launcher's `@("-m", "cli.main", "analyze")` (`scripts/start_tradingagents.ps1:115`) now fails with
  `No such command 'analyze'` and exit 2. I reproduced this with a minimal Typer app of the same shape:
  `analyze --checkpoint` exits 2, and a bare `--checkpoint` runs. The fix is to drop `"analyze"`.
- **The dependency change is stale.** Upstream main declared `python-dotenv>=1.0.0` on 2026-06-13
  (2a58c22, `pyproject.toml:19`). The PR's line (`pyproject.toml:23` on the PR head) duplicates it, and
  the dependency list has changed since (`parsel` and `redis` are gone), so expect a conflict despite the
  cached `MERGEABLE`.
- **A bad venv is never rebuilt.** If `py -3` picks a Python older than 3.10, the check at `:65` throws,
  but `.venv` stays. Every later run then fails the same way until the user deletes `.venv` by hand.
- **The staleness marker only watches `pyproject.toml`.** A `git pull` that changes only code is fine
  (editable install), but a dependency bump that arrives without an mtime change (restore, copy) is missed.
  `uv run`/`uv sync` compare the lockfile instead, which is the sturdier way.
- **Minor.** On failure the `.bat` stops at `pause` (`start_tradingagents.bat:6-8`), which blocks
  scripted use. `-ExecutionPolicy Bypass` is a normal choice for a local launcher. None of this touches
  point-in-time data or look-ahead.

## Value to Berkshire

Little, and Berkshire is already better here:

- **The launcher idea is already built in.** `bin/berkshire:5` runs
  `uv run --quiet --extra tui --project "$root" python -m berkshire "$@"`. uv creates the environment on
  first use, re-syncs it whenever `uv.lock` changes, and selects a matching Python (`requires-python >=3.11`,
  `pyproject.toml:5`). This does everything the PR's 127 lines of PowerShell do, with no marker file.
  Claude Code puts the plugin `bin/` on PATH. On Windows, Claude Code's Bash tool runs in Git Bash, so a
  `#!/bin/sh` wrapper plus uv should resolve there too (not tested).
- **No `.env` step.** Berkshire has no provider API keys. Models are Claude subagents (D1), and eToro
  goes through the MCP (D2/D3).
- **No interactive CLI to launch.** The entry points are `/berkshire:*` skills inside Claude Code.

Would Berkshire work on Windows at all? The launcher is not what stands in the way. The engine and CLI
path is plain Python and should work. The dashboard server and client use POSIX-only process calls, and
these break on native Windows Python:

- `berkshire/client.py:21`: `os.kill(pid, 0)` is not a liveness probe on Windows. Signal 0 is
  `CTRL_C_EVENT` there, so it sends a console Ctrl+C instead of checking the pid. This breaks
  `discover()` and `ensure_server()` (REQ-UI-11).
- `berkshire/server.py:285`: `os.killpg` does not exist on Windows. The resulting `AttributeError` is not
  caught, so stopping a dashboard job fails (REQ-UI-13).
- `berkshire/server.py:274`: `ps -o command=` does not exist, so every job reads as `exited`.
- `berkshire/server.py:293` and `berkshire/client.py:51`: `start_new_session=True` has no process-group
  effect on Windows.
- `berkshire/server.py:449`: `os.chmod(reg, 0o600)` only sets the read-only bit on Windows. The 0600
  claim in REQ-UI-02 does not hold there, though the user-profile ACLs mostly cover it.

None of these follow from this PR, and D7 (a local `/loop` on the user's machine) does not name a
platform. The PR does not change that picture.

## Proposed Berkshire change

None. The wrapper plus uv already provide lazy setup, dependency sync and interpreter selection, and
Berkshire has no `.env` step and no interactive CLI to start. If Windows becomes a target, the work is
in the dashboard process handling above: a `sys.platform` branch using `psutil` or
`CREATE_NEW_PROCESS_GROUP`/`taskkill /T`, plus a platform note in the README. It would not be a launcher,
and it should be decided on its own, not taken from this PR.

## Effort and risk

Nothing to do, so zero effort (S). For reference, Windows support for the dashboard would be M: about a
day for three call sites, their tests, and a Windows CI leg to prove it. It is low risk if the POSIX path
stays unchanged.

## Open questions

- Is Windows a supported platform for Berkshire at all? If yes, add a requirement (for example a
  REQ-UI or install row that names the supported platforms) and a Windows CI job before touching the

- Does Claude Code on Windows reliably run an extensionless `#!/bin/sh` plugin `bin/` script from its
  Git Bash shell? This is untested here, and a `bin/berkshire.cmd` twin would be the fallback.
