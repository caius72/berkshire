# TradingAgents PR #1074: retry an undecodable JSON response body instead of aborting the run

- Head: `5101813cbfd6` · Author: Lotus2077 · Opened 2026-06-22, last activity 2026-06-30
- Files: `tradingagents/llm_clients/openai_client.py`, `tradingagents/graph/trading_graph.py`,
  `tradingagents/default_config.py`, `tests/test_llm_retry.py`, README, CHANGELOG (+181/-1)

## Summary

**Verdict: decline.** This is a transport-level retry for the OpenAI SDK. Berkshire has no
transport layer of its own, and Claude Code handles API retries. The two Berkshire analogues are
already covered: a subagent step that errors is re-run once, and a missing or broken JSON block
falls back to free text and then to `REVIEW`. Neither needs a new retry.

## What it does

`NormalizedChatOpenAI.invoke` now wraps `super().invoke()` in a loop that catches only
`json.JSONDecodeError`. That is the case where a 2xx response's `application/json` body is
truncated or garbled. The OpenAI SDK parses the body once, after its own HTTP retry loop, so this
error would otherwise escape a graph node and abort the whole run. The loop's budget is
`self.max_retries`, with capped exponential backoff (1, 2, 4, 8 s) and a `logger.warning` on each
retry (`openai_client.py:55-72` at head). The PR also adds two config keys:
`llm_max_retries` and `llm_timeout`, with the matching `TRADINGAGENTS_LLM_*` environment variables
(`default_config.py:107-108`). `_get_provider_kwargs` coerces them and passes them to the client
(`trading_graph.py:163-169`).

The first version also caught the SDK's HTTP-transient errors, which multiplied the retry budget
to about 9 requests. It also claimed to cover structured-output parse errors. After the Gemini
review, the author narrowed it to the single `JSONDecodeError` case.

## Soundness

- **The retry never runs with the default config (the reviewer's finding, and I agree).** The
  code at `openai_client.py:60` is `attempts = max(self.max_retries or 0, 0) + 1`. The shipped
  default is `llm_max_retries: None` (`default_config.py:107`), and `trading_graph.py:164` only
  forwards a value that is not `None`. That leaves the LangChain `max_retries` field unset, so
  `attempts == 1` and the loop makes one attempt. The feature does nothing unless the user sets
  `llm_max_retries`. praxstack posted a patch with a `_DEFAULT_INVOKE_RETRIES = 2` fallback and
  three tests. The author has not applied it.
- **The tests hide this.** Every test builds the client with
  `model_construct(max_retries=N)` (`tests/test_llm_retry.py:30`), so the default path is never
  exercised.
- **Setting `llm_max_retries` changes two things at once.** It sets the SDK's HTTP retry count
  and the budget of this outer loop. The two cannot be tuned separately. The narrowing still means
  they no longer multiply, because each loop catches different errors.
- **Some comments were not updated after the narrowing.** `default_config.py:100-106` and
  `trading_graph.py:159-162` still say "transient parse/timeout failures". The code no longer
  retries timeouts.
- **Coverage is narrow.** Only the OpenAI-compatible client gets the retry. Anthropic and Google
  do not, and neither does `ainvoke`. `time.sleep` blocks the calling thread, which is acceptable
  for LangGraph's synchronous nodes.
- **No look-ahead risk.** The change touches transport only. The failure behaviour is bounded:
  once the budget is used up, the original error is raised again.

## Value to Berkshire

Very little. Berkshire makes no LLM API calls itself. Every role is a Claude Code subagent, and
Claude Code owns the transport and its retries. A garbled HTTP body never reaches the engine.
These are the Berkshire analogues:

1. **A subagent step errors or writes no output file.** This is already covered by the
   dispatcher rule in `skills/analyze/pipeline-loop.md:28-30`: re-run that one step once, and if
   it fails again, stop with state kept so that `--checkpoint` resumes. It is the same "retry
   once, then fail with state preserved" idea as the PR. The input check sits in `cli.py:102-103`
   and `pipeline.py:394-395`. One tick instrument failing does not stop the others
   (REQ-SCHED-05, `skills/tick/SKILL.md:29`).
2. **The structured JSON block is missing or invalid.** This is not transient in the PR's sense.
   The model produced complete output, just not in the requested shape. Berkshire handles it on
   purpose. `decisions.structured()` falls back to the free text (`decisions.py:175-192`,
   REQ-OUT-02). `submit` records a warning (`pipeline.py:397-402`). For the Portfolio Manager, the
   rating is then parsed from that free text (`pipeline.py:436`). Only when no rating can be found
   does the signal become `REVIEW` (`decisions.py:44-45`, REQ-OUT-05). `REVIEW` places no order
   and is flagged for a human (`orders.py:30-31`). This is a fail-safe outcome, not a crash, so
   there is no aborted run for a retry to rescue.

The only retry idea that could transfer is re-asking the Portfolio Manager once when its output
would give `REVIEW`. That costs one extra Opus call and could save one instrument-day in a tick.
There is no evidence that it is needed: the local run history has no `REVIEW` signals and no
structured-output warnings. It would also weaken a deliberately simple rule: an unparseable
decision goes to a human. Berkshire is already better placed here than upstream, whose
non-structured nodes have no fallback at all.

## Proposed Berkshire change

None. The transport retry has no counterpart in Berkshire. Both Berkshire failure modes already
have a defined, tested outcome.

Revisit if either signal becomes common in real runs: `REVIEW`, or the Portfolio Manager's
"used free text" warning (more than a few percent of tick decisions). The change would then be a
one-shot re-prompt in `pipeline.submit` for `portfolio_manager` when `parse_rating` gives
`REVIEW`: reject once with a "JSON block missing, answer again" error, and accept and fall back
on the second try. REQ-OUT-05 would be amended, with one test. Effort S.

## Effort and risk

No change is proposed. The hypothetical PM re-prompt above is effort S (< 2 h, `pipeline.py`
plus one test and an amendment to REQ-OUT-05). Its risk is low but not zero. It adds a
second state path to `submit`, and it could hide a persona regression that `REVIEW` currently
makes visible.

## Open questions

  (`pipeline.py:394-395`). The rule should probably cover both, and the rule has no `REQ-*` row
  or test of its own. This is a small wording and traceability tidy-up that is independent of
  this PR.
