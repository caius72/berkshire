# PR #1195: feat(llm): add openai_codex provider using ChatGPT subscription quota

Head `0ced629003d9`, by LeonWTW, opened 2026-08-01, last updated 2026-09-18. +1004/−19 across 15 files. Closes issue #1194.

## Summary

**Verdict: decline.** This is OpenAI provider plumbing for an undocumented ChatGPT-subscription endpoint. Berkshire is Claude-only (D1, REQ-ROLE-02) and runs its roles as Claude Code subagents, so there is no provider layer for it to plug into. The one side idea, a login check before the run, is already covered in Berkshire.

## What it does

- **New provider.** It adds an `openai_codex` provider so that TradingAgents LLM calls are billed to a ChatGPT subscription instead of API credits.
- **Credentials.** `tradingagents/llm_clients/codex_auth.py` reads the OAuth token that the Codex CLI keeps in `~/.codex/auth.json`. It refreshes the token when it is within 300 s of expiry. The refresh token rotates, so the module writes the new one back to the file under an `flock` (`codex_auth.py:220-258`).
- **Request shape.** A `CodexChatOpenAI` subclass forces `stream=True` and `store=False` and drops `temperature`. It also relabels every `system` input item as `developer`, because the endpoint answers `system` with HTTP 400 (`openai_client.py`, `_get_request_payload`, diff hunk around line 1121).
- **CLI.** The picker gets a new entry, plus a check that fails early with "run `codex login` first" instead of a 401 part-way through a run.

The problem it solves is token cost for people who already pay for ChatGPT.

## Soundness

The code is careful for what it is: the file is re-read and re-validated under the lock, the write is atomic, and every error comes with an actionable message. But it has real problems:

- **The token file is briefly readable by other users.** `_write_auth` creates `auth.json.tmp` with the process umask (usually 0644), writes the live tokens into it, and only then calls `chmod` to the original mode (`codex_auth.py:158-166`). For that short window, other local users can read the access and refresh tokens. The fix is `os.open(tmp, O_WRONLY|O_CREAT|O_TRUNC, mode)`.
- **The lock does not cover the official Codex client.** The `.lock` sidecar (`codex_auth.py:169-185`) only serialises TradingAgents processes. The Codex CLI does not take that lock. If both refresh at the same moment, one of them spends a refresh token that has already been rotated, and the user gets logged out. That is exactly the failure the module sets out to prevent.
- **The endpoint itself is unstable.** It is undocumented and unversioned, and the PR's own README says it often returns "servers are currently overloaded". Scheduled runs on it would be fragile.
- **No trading-logic effect.** Point-in-time and look-ahead safety are not affected: nothing in the trading logic changes.

- **Tests.** There are about 560 lines of tests: auth resolution, refresh and rotation, payload shaping, the CLI check, and an opt-in live smoke test.

- **Merge state.** The branch is `CONFLICTING` and has no reviews.
- **Maintainer position.** Yijia-Xiao commented on 2026-09-18: "We are not shipping this while it depends on an undocumented endpoint and on reading and rewriting the Codex client's credential file, which the provider has not sanctioned." The PR is kept open only in case OpenAI documents subscription-backed API access.

The chance that it merges in this form is close to zero.

## Value to Berkshire

None:

- **Nothing to plug into.** Berkshire has no LLM provider layer. Models are Claude aliases picked per role (`berkshire/config.py:13`, `berkshire/pipeline.py:277`), and Claude Code runs them under the user's own Claude plan. The cost problem this PR solves is already solved by that design.
- **The system-to-developer role fix does not transfer.** Berkshire never builds a raw API payload.
- **The login check is already covered.** The Claude Code session is authenticated before any skill runs. The eToro MCP is the only external dependency that needs auth, and it is not touched here.
- **Hard fit conflict.** Reading and rewriting another tool's credential file goes against D1, and against Berkshire's stance of not handling credentials it does not own.

## Proposed Berkshire change

None. It is OpenAI-only provider plumbing, it conflicts with D1 and REQ-ROLE-02, and it has no idea that is independent of the provider.
